무엇을 만드는가

말로 물으면 데이터에서 찾아 답한다. 그런데 데이터가 세 가지 형태로 나뉘어 있어서, 찾기 전에 어디서 찾을지부터 정해야 한다.

과제가 준 데이터는 하나의 데이터베이스가 아니라 서로 다른 형태의 세 자산입니다. 같은 회사의 운영 데이터인데, 담긴 방식이 다릅니다.

분업선 — 고르는 건 규칙, 쓰는 건 LLM

도구를 고르는 일은 규칙이 하고, 문장을 쓰는 일만 LLM이 한다. 이 경계선이 시스템을 네 층으로 가른다.

제약이 먼저입니다. 외부 API를 쓸 수 없고(OpenAI·Claude 금지), 모델은 Ollama 로컬 실행이며, 권장 개발 환경은 GPU 선택 · RAM 최소 4GB입니다. 즉 판단을 맡길 수 있는 모델이 작습니다. 그리고 과제는 “규칙 기반 라우터”를 명시합니다.

두 사실이 같은 곳을 가리킵니다. 도구 선택을 소형 LLM에게 맡기지 않습니다. LLM은 마지막에 답변 문장을 만드는 일만 합니다.

이 “4GB”는 실측으로 되짚어야 했습니다. 권장 모델 gemma4:e2b-it-qat을 CPU 전용으로 올리면 단독 4.0GB이고(2026-08-18, num_gpu:0 강제) 임베딩까지 얹으면 4.4~5.2GB입니다. RAM 4GB로 CPU 전용 구동은 안 됩니다. 다만 원문을 다시 읽으면 그 조합이 의무가 아닙니다 — 표의 LLM 실행 값이 “GPU 선택”이고 본문도 “CPU만으로도 구동 가능”이며, RAM 최소 4GB는 블로그 한 곳의 “권장 개발 환경”(=개발 기계) 표에만 있습니다. 심사 실행기 사양을 적은 문면은 어디에도 없습니다. 대응은 열린 항목입니다.

dataset-analysis.md · design.md

확정된 것

  • 라우터는 에이전트 밖, MCP 서버 측 도구다. 판별 로직이 서버에 있고 에이전트에는 없습니다. 데이터셋 README의 도구 매핑 표가 라우터를 “MCP 도구”로 표기합니다.
  • 등록 도구는 4개다. 라우터 + 도구 3종 전부를 MCP 도구로 등록합니다. 라우터만 노출하면 “3개의 MCP 도구를 구현합니다”라는 문면을 미충족으로 해석할 심사 리스크가 있습니다.
  • 스택은 공식 MCP SDK 직접 사용. 주최사 프레임워크 air는 실제로 설치해 돌려본 뒤 기각했습니다.

부수 효과 — 에이전트 입장에서 선택지가 하나다

이 배치의 이득은 “규칙이 더 정확해서”가 아닙니다. 에이전트가 도구 선택 문제를 아예 겪지 않는다는 점입니다. Mem2ActBench(arXiv:2601.19935)는 후보 도구가 1 → 2 → 5개로 늘 때 hard negative 조건에서 선택 정확도가 94.5% → 78.0% → 69.75%로 떨어짐을 보입니다. 다만 같은 실험에서 random negative는 93.5~95.5%로 변화가 없었습니다 — 원인은 후보 개수 자체가 아니라 의미적으로 겹치는 후보의 존재입니다. 인용할 때는 개별 점(69.75%)이 아니라 같은 후보 수에서 두 조건이 24.75%p 벌어졌다는 대조를 씁니다 — 개별 점은 반복 실행 분산 안에 들어갑니다.

그리고 ③에서 보듯 우리 도구 3종은 정확히 그 hard negative 관계입니다.

다만 이 이득은 조건부입니다. 라우터가 도구를 직접 실행하거나(A안), 라우터의 지시를 코드가 집행할 때(B안 중 B2)만 성립합니다. 라우터가 고른 도구를 LLM이 다시 읽고 호출하는 방식(B1)이면 후보 4개 조건 그대로이며, 이것이 B1을 권하지 않는 이유입니다. 그리고 이 조건을 강제하는 것은 프로토콜이 아닙니다 — 도구 4개를 등록하면 tools/list에 4개가 전부 보이고 서버는 클라이언트가 무엇을 호출할지 막을 수 없습니다. 라우터 경유는 에이전트 코드에 하드코딩해야 하고, 프롬프트 지시로 두면 소형 LLM에서 샙니다(엣지 Q4).

라우터 배치 미정 · 구조

라우터가 도구를 직접 실행하는지(A안 게이트웨이형), 어느 도구를 쓸지만 알려주는지(B안 조언자형). 위 확정 사항은 두 안 모두 만족합니다. 공통부 구현 후 재평가하기로 했고, 근거는 ⑤에 있습니다.

무엇을 기준으로 고르는가

질문이 어느 자산에 있는가가 아니라 어떤 형태의 답을 요구하는가로 도구를 가른다. 자산으로 가르는 방법은 이 데이터셋에서 성립하지 않는다.

가장 자연스러운 설계는 “도구 하나에 자산 하나”입니다. 벡터 검색은 문서를, NL2SQL은 테이블을, 지식 그래프는 그래프를 맡는 식입니다. 데이터를 세어 보기 전에는 이 방법에 문제가 없어 보입니다. 세어 보면 무너집니다.

세 자산이 얼마나 겹치는가 — 실측
확인한 것결과뜻
그래프 관계 7종을 테이블에서 도출해 집합 단위로 대조 7종 전부 집합 일치 그래프는 새 정보를 담고 있지 않다. 테이블 관계의 비정규화 재표현이다. 지식 그래프 질문 10개는 전부 SQL로도 답할 수 있다.
문서 40건이 그래프 개체를 언급하는가 40 / 40 문서만 읽어도 개체가 나온다. 문서를 “문서 전용 질문”으로만 묶을 수 없다.
support_tickets의 title 28종이 문서 본문과 주제어가 겹치는가 18 / 28 같은 주제를 티켓은 목록으로, 문서는 서술로 갖는다.

즉 자산으로 도구를 가르면, 겹치는 구간에서 규칙이 정의되지 않습니다. 그래서 경계를 다른 축으로 그었습니다.

판별 규칙

라우터의 규칙 — 질문이 무엇을 돌려받길 요구하는가
#질문이 요구하는 것도구
1서술 — 원인, 방법, 절차, 내용, 결정, 제안 vector_search
2정형 속성·수치 — 금액, 연봉, 기간, 상태, 행 개수 nl2sql
3개체 식별·연결 — 누가 / 무엇을 / 어디 소속 / 담당 knowledge_graph
4관계를 세는 집계 — 세는 대상이 관계이므로 규칙 3에 귀속 knowledge_graph

이 규칙을 questions.json 30개에 대조한 결과 29/30이 일치합니다 (vector_search 10/10, nl2sql 9/10, knowledge_graph 10/10).

유일한 불일치 #5는 우리 규칙의 결함이 아니라 데이터셋 내부 비일관성입니다 — #25·#29와 구조가 같은 관계 카운트의 최대인데 배정만 반대입니다. 어떤 원칙적 규칙도 셋을 동시에 만족시킬 수 없고, 규칙 4를 뒤집으면 그 두 건이 대신 틀려 28/30이 됩니다. 29/30이 원칙적 규칙의 상한이므로 예외를 넣지 않고 알려진 불일치로 문서화합니다.

규칙이 이 축을 쓰면 도구 설명(description)도 같은 축으로 써야 합니다. 자산으로 설명하면 설명끼리 겹쳐 그 자체가 hard negative가 됩니다.

그런데 실제로 가르는 것은 “피연산자”다

위 표는 출력 형태로 쓰여 있는데, 그것만으로는 두 도구가 갈리지 않습니다. #9 “평균 연봉이 가장 높은 부서는?”의 답은 부서, 즉 개체인데 정답은 nl2sql입니다. knowledge_graph도 개체를 냅니다. 갈리는 지점은 무엇을 세느냐입니다 — 속성이냐 관계냐.

규칙 4가 이미 그렇게 쓰여 있습니다: “세는 대상이 관계이므로 규칙 3에 귀속”. 그리고 데이터가 이를 확인합니다 — 집계 질문 10건을 피연산자로 가르면 속성 집계 7건은 예외 없이 nl2sql이고, 관계 집계 3건만 nl2sql 1 / knowledge_graph 2로 갈립니다. 그 예외 하나가 #5입니다.

그래서 코드는 무엇을 보고 판정하는가 — 스키마 어휘

규칙 4개는 의미로 쓰여 있습니다. 코드가 볼 표층 신호는 스키마의 관계명·컬럼명에서 뽑습니다 — 관계 7종 (USES · BELONGS_TO · MANAGES_ACCOUNT …)과 테이블 컬럼 (amount · salary · status …).

이 길만 규칙에 허용됩니다. 스키마는 질문보다 먼저 있던 구조라 인스턴스 역산이 아닙니다. 반면 30개 질문에서 키워드를 뽑는 것은 금지입니다 — 30개는 회귀 전용이고 결함 2건을 포함하며, 그것으로 규칙을 만들면 규칙을 검증할 수단이 사라집니다. 후보였던 의문사 매핑(어떻게/왜→서술, 누구/어디→개체)은 대조 결과 실패했습니다 — 개체 태그가 두 도구에 걸치고 9건이 무태그입니다.

거친 1차 구현으로 28/30이 나옵니다. 미스는 #5(알려진 데이터셋 불일치)와 #17 (REPORTED_ISSUE의 “이슈”가 일반 명사와 충돌 — 엣지 R5) 둘입니다. 다만 이 28/30을 실력으로 치지 않습니다 — 한국어 표층형 매핑을 사람이 썼고 그 사람이 30개를 이미 읽은 뒤였습니다. 자체 엣지 세트로 다시 재기 전까지는 “방향이 맞다”까지만 주장합니다.

겹치면, 없으면 어떻게 되는가

겹침에는 두 종류가 있고 처리가 정반대다. 두 도구가 같은 답을 내는 겹침은 하나만 부르고, 서로 다른 조각을 내는 겹침은 둘 다 불러 합친다.

③에서 경계를 그었지만, 겹침 자체가 사라지지는 않습니다. 규칙이 어느 도구를 고를지는 정해지되, 다른 도구도 뭔가를 갖고 있는 상황은 남습니다. 그 상황이 다섯 갈래입니다.

병렬은 과제 요구가 아니다

여기서 용어를 하나 갈라 둡니다. 요강에는 “규칙 기반 라우터를 통한 도구 자동 선택 (MCP Parallel 패턴)”이라는 항목이 있습니다. 이 괄호 표기 때문에 병렬 호출이 과제 요구처럼 읽히기 쉬운데, 출처 3곳과 데이터셋을 전수 검사한 결과는 다릅니다.

“병렬” / “Parallel” 출현 전수 검사

어느 출처도 무엇이 병렬인지 정의하지 않습니다. 블로그의 라우터 서술(“적합한 도구를 자동 매칭” — “호출”이 아닙니다)은 수를 명시하지 않습니다. 한국어는 복수 표지가 선택적이라 “도구를”은 단수·복수 어느 쪽으로도 읽힙니다. 수를 정하는 것은 문면이 아니라 스키마입니다 — questions.json 30개의 tool이 배열이 아니라 문자열입니다(30/30, 예외 0건).

그래서 우리는 병렬을 요구가 아니라 설계 선택으로 규정합니다. 근거는 문면이 아니라 상보 중복 실측입니다 — X3·X4 구간에서는 한 도구만으로 답이 완성되지 않습니다. 반대로 X1·X2에 병렬을 걸면 같은 답을 두 번 받아 토큰만 두 배가 되고, 중복 컨텍스트 추가가 정확도를 떨어뜨린다는 Pylon-7의 L2.5 ablation에 정면으로 걸립니다.

이 구분의 이득은 “왜 병렬을 했는가”뿐 아니라 “왜 X1·X2에는 병렬을 안 했는가”도 데이터로 설명된다는 점입니다.

X5는 예외가 아니라 정상 경로다 — 그리고 도구 3종 전부에 있다

커버리지를 개체 단위로 세면 놓칩니다. 문서가 커버하는 제품은 10/12지만, 주제를 2개 이상 가진 제품은 0개입니다 — Product-C1은 설치 가이드만, Product-D1은 API 레퍼런스만 있습니다. 그래서 (개체 × 요구 형태) 격자로 재야 합니다.

응답은 여섯 상태, 두 계층

MCP 스펙의 에러 2계층에 대응시킵니다. “데이터에 없음”과 “시스템 오류”는 다른 응답 타입이라는 것이 공통 규약입니다.

거절 · 부재 응답 스키마 미정 · 구조

위 다섯 상태를 어떤 필드 구성으로 표현할지가 아직 열려 있습니다 — 플래그·확신도·이유 문구의 조합. 부분 응답 스키마와 형태를 맞춰야 합니다. 이 항목은 문헌 2건 (Wen et al. TACL 2025 · When2Call NAACL 2025)이 닫습니다.

부분 응답 스키마

④의 X5가 실제로 어떻게 나가는지입니다. 핵심은 “요구 유형의 자료 없음”과 “확인된 인접 사실”이 별도 필드라는 점입니다. 

{
  "status": "partial",
  "requested_form": "narrative",
  "unavailable": { "asset": "documents", "reason": "no_document_for_entity" },
  "adjacent_facts": { "source": "knowledge_graph", "data": [ /* ... */ ] }
}

필드를 나누지 않으면 어떻게 되는지가 이 스키마의 존재 이유입니다. 원인을 물었는데 “이슈가 있었다”는 사실만 주면, 응답만 보고는 모델이 그것이 원인인지 인접 사실인지 구분할 수 없습니다. 그러면 소형 LLM이 그로부터 원인을 지어냅니다. 에이전트 규약은 “원인 기록은 없습니다. 다만 …한 기록은 있습니다”입니다.

라우터 배치 — 두 안

A안 게이트웨이형 vs B안 조언자형 보류 · 재평가 예정

확정되어 흔들리지 않는 전제: 라우터는 에이전트 밖 MCP 도구이고, 도구 선택은 규칙이 하며, 등록 도구는 4개입니다. 두 안 모두 이를 만족합니다. 갈리는 것은 판별한 뒤 도구를 직접 실행하는가뿐입니다.

비대칭이 하나 있습니다. B안의 가시성은 A안에서 structuredContent에 routed_to·matched_rule을 실어 상당 부분 회수되지만, A안의 복잡도 집중은 B안에서 회수할 방법이 없습니다 — 에이전트가 병합을 하는 것은 구조적입니다. 이 비대칭 때문에 A안이 근소하게 앞선다고 보되, “명확하다”고는 말하지 않습니다.

그래서 왜 지금 안 정했는가

선택의 핵심 입력 두 가지가 만들어 봐야 손에 들어오기 때문입니다 — 병렬(X3·X4)이 실제로 얼마나 자주 발동하는가(잦으면 B안의 가시성 이점이 커지고, 드물면 A안의 단순함이 이깁니다), 부분 응답 조립이 얼마나 지저분한가(복잡하면 A안으로 모아야 하고, expected_form 스키마로 깔끔하게 떨어지면 B안 부담이 사라집니다).

그리고 미루는 비용이 0입니다. 도구 3종 핸들러·규칙 판별 함수·부분 응답 스키마는 두 안에서 동일하고 이것이 작업량의 대부분입니다. 지금 닫으면 정보 없이 닫는 것입니다. 재평가 시점은 공통부 완성 및 라우팅 축 29/30 확인 직후, 에이전트 착수 전입니다.

그래프 적재 방식 미정 · 구조

그래프가 테이블에서 100% 도출되므로 nodes/edges를 별도 테이블로 적재하지 않고 기존 테이블 위 뷰로 구성할 수도 있습니다. 다만 “온톨로지 기반” 요구에는 명시적 테이블이 설명하기 쉽습니다. 문헌이 아니라 스키마를 짜 보고 정합니다.

임베딩 모델후보 bge-m3 후보를 nomic-embed-text에서 바꿨습니다 — 출처 3곳에 모델명이 없고(2026-08-14 재확인, 실제 출현은 데이터셋 README의 “또는 다른 임베딩 모델” 예시 한 줄), nomic은 모델카드 언어 태그가 en 하나입니다. bge-m3는 피어리뷰 다국어 실증(Findings of ACL 2024, MIRACL ko 72.1)이 있고 컨텍스트가 8K입니다. 메모리 실측은 끝났습니다 — CPU 전용으로 bge-m3 1.2GB 대 nomic 376MB인데, LLM과 합치면 둘 다 4GB를 넘어 메모리로는 갈리지 않습니다. 남은 것은 적재 후 검색 품질 비교와 차원 — 배포 스키마가 vector(768)이라 1024차원인 bge-m3는 DDL 변경이 따라옵니다
LLM 모델확정 gemma4:e2b-it-qat 블로그·공지가 동일 문면으로 Gemma 4 E2B (Ollama 로컬 실행)을 명시하고 레지스트리에 실물이 있습니다. KOSSA 요강의 “7B” 차이는 존속하지만 문의 대상에서는 뺐습니다 — 리원에이스 2출처가 일치해 문의로 얻을 정보가 없습니다. 태그는 최소인 e2b-it-qat(4.3GB)로 정했고, CPU 전용 실측도 끝냈습니다(4.0GB · 100% CPU). e2b(7.2GB) 상향은 뺐습니다 — 최소 태그가 이미 하한에 닿았습니다
RAM 4GB 하한 대응미정 — 실측이 미달을 확인 CPU 전용 실측: LLM 단독 4.0GB, +nomic 약 4.4GB, +bge-m3 5.2GB. 여기에 OS·PostgreSQL·MCP 서버가 더 붙고, 컨텍스트 2048 기준이라 하한입니다(기본값은 131072). 다만 같은 날 문면 재확인이 제약을 느슨하게 만들었습니다 — GPU는 “선택”이고 CPU 전용은 가능 서술이지 의무가 아니며, RAM 최소 4GB는 블로그 한 곳의 개발 기계 사양입니다. 남은 선택지는 둘 — 모델 교체(로컬에 exaone3.5:2.4b 1.6GB 실물)와 순차 적재(최대치 4.0GB는 안 줄고 재적재 지연이 붙습니다). 태그 축소는 불가합니다. 닫는 조건은 심사 실행 환경 확인이라 문의 후보로 올렸습니다
MCP transportstdio로 시작 심사 시연에 원격 접근이 필요하면 Streamable HTTP 추가 검토. 프로토타입에서 stdio 동작 확인됨
유사도 임계값 T4미정 논문으로 정할 수 없다. 자체 엣지 세트로 실험하되 questions.json에서 역산하지 않는다
nl2sql 재시도 T1제약 하나 확정 재시도는 실행 오류 메시지 같은 외부 신호를 반드시 물어야 하고, 자기교정 루프는 금지 (Huang et al., ICLR 2024). air의 retryPlugin은 쓸 수 없다
엔티티 정규화 수준 T5미정 데이터셋 개체명이 전부 Client-A~Client-AD 합성 패턴이라 문헌으로도 데이터로도 안 닫힌다 — 자체 엣지 세트로 정한다
TACC 적용 세부방향 확정 적용 지점은 라우터 반환 컨텍스트 선별 하나. 테이블이 8개뿐이라 nl2sql 스키마 선별은 대상이 아니다. 병렬 병합·부분 응답이 반환량을 늘려 이 지점의 중요도가 크다

검증은 두 세트로 나눈다

questions.json 30개는 회귀 전용이고 규칙 튜닝에 쓰지 않습니다. 30개에 맞춰 규칙을 고치면 그게 곧 과적합이기 때문입니다. 그리고 회귀는 하나의 점수가 아니라 두 축으로 잽니다 — 데이터셋 결함 2건의 성격이 다르기 때문입니다.

회귀 2축
축기대값알려진 예외
라우팅 축 — 고른 도구가 기대 도구와 같은가 29 / 30 #5 — #25·#29와 구조가 같은데 배정이 반대. 예외 규칙을 넣지 않고 문서화한다
실행 축 — 선택된 도구가 올바른 응답 유형을 내는가 30 / 30 #23(“서울물산”) — 존재하지 않는 개체명. 정답을 “결과 반환”이 아니라 “개체 부재(T5) 응답”으로 재정의하면 실패 케이스가 아니라 검증 실물이 된다

나머지는 자체 엣지 세트가 맡습니다. 데이터셋이 작고 정형적이라 30개로는 검증되지 않는 것들이 있습니다 — 존재하지 않는 개체명(T5), 관계 카운트 애매(X1), 부분 응답(X5), 무매칭·스몰토크(R1, 30개 중 0건), 병렬 대상 질문(X3·X4, 30개 전부 tool 단수라 검증 수단 자체가 없음).

그 세트를 1차 29문항으로 작성했습니다 (2026-08-14). 기대값을 “기대 도구 1개”가 아니라 도구 배열 + 응답 상태로 두어 거절(도구 0개)·부분 응답·의존 질문까지 담았고, 채점은 회귀와 같은 2축입니다. 판정 LLM은 쓰지 않습니다 — 기대값이 결정적 라벨이라 검증이 집합·문자열 비교로 끝나므로, LLM 판정의 편향을 스키마 설계로 원천 회피합니다.

역산이 아니라는 것은 세 가지로 남깁니다. 생성 입력(페르소나 카드·골격 매트릭스·프롬프트 템플릿)이 커밋 실물로 있고 그 안에 questions.json이 없다는 것, 골격 커밋이 문면 커밋보다 먼저라는 git 히스토리, 그리고 회귀 30개와의 문자 3-gram 자카드 최대값이 0.212(임계 0.5)라는 기계 대조입니다. 다만 골격 작성자가 30개를 이미 읽었다는 오염은 제거되지 않았습니다 — 배제되는 것은 표절형 역산까지입니다.

세트 실물과 작성 절차·역산 방지 규약은 edge-set/README.md와 edge-set/edge-questions.json에 있습니다.
