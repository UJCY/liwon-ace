# 구조 엣지케이스 카탈로그

> 설계 결정 배경은 [design.md](./design.md) D3·D6·D7·D9·D10 참조. 데이터 근거는 [dataset-analysis.md](./dataset-analysis.md).

## 원칙 — 무엇이 허용되는 분석인가

| 레벨 | 정의 | 허용 |
|------|------|------|
| **구조 레벨** | 데이터셋 내용을 몰라도 성립하는 시스템 실패 유형. 어떤 데이터가 와도 존재하는 케이스 | ✅ 분석·설계 반영 |
| **인스턴스 레벨** | questions.json 30개 개별 질문, 문서 40건 개별 내용에 맞춘 튜닝 | ❌ 금지 (과적합) |

**경계선**: 자산 간 **구조를 대조**하는 것(무엇이 어디에 중복되는가)은 구조 레벨이므로 허용된다. 개별 질문에서 **규칙을 역산**하는 것이 금지다. 카테고리 1은 전자로 도출됐다.

**측정 방법**: 커버리지는 개체 1차원이 아니라 **(개체 × 요구 형태) 격자**로 잰다. 1차원 카운트는 2차원 희소성을 숨긴다 — "제품 10/12 커버"가 실제 10/60을 가렸다.

이 문서의 케이스 서술에 특정 질문·특정 문서가 등장하면 그 케이스는 잘못 작성된 것이다. (예외: 데이터셋 결함 2건은 회귀 기준을 정하기 위해 식별자로 언급한다.)

## 카테고리 1 — 자산 중복과 요구 형태 미충족

세 자산이 같은 사실을 다른 형태로 담고 있어 생기는 케이스. **어떤 데이터셋이든 여러 자산을 두면 발생하는 구조 문제**다.

### 중복 — 두 도구가 같은 질문에 답할 수 있다

| ID | 케이스 | 겹치는 자산 | 두 도구의 답 | 기대 동작 |
|----|--------|-----------|------------|----------|
| **X1** | **관계를 세는 집계** — "X별 ~수가 가장 많은 것은?" | 테이블 ↔ 그래프 | **같다** | **단일 선택.** 관계를 세므로 `knowledge_graph` (D9 규칙 4) |
| **X2** | **관계를 따라가는 조회** — "A의 B는?" | 테이블 ↔ 그래프 | **같다** | **단일 선택.** 관계만 물으면 `knowledge_graph`, 정형 속성이 함께 걸리면 `nl2sql` (D9 규칙 2·3) |
| **X3** | **사건 조회 + 서술 요구** — "~ 관련 장애가 있었**고 원인이 뭐야?**" | 테이블(티켓) ↔ 문서 | **다르다** — 티켓은 사건 *목록*, 문서는 원인·조치 *서술* | **병렬 호출 후 병합** (D3) |
| **X4** | **개체 지목 서술** — "특정 개체의 ~는?" | 그래프/테이블 ↔ 문서 | **다르다** — 사실 vs 서술 | **병렬 호출 후 병합** (D3) |

**X1·X2에 병렬을 걸지 않는 이유**: 그래프가 테이블의 파생이라 같은 답이 두 번 온다. 토큰만 2배이고, 중복 컨텍스트 추가가 정확도를 떨어뜨린다는 Pylon-7 L2.5 ablation에 걸린다.

**존재 확인 단독은 X3가 아니다.** *"SSL 인증서 관련 장애가 있었어?"*(`questions.json #19`)는 요구 원소가 **1개**(존재/서술)이므로 단일 호출이고, 실제 배정도 `vector_search` 단독이다. X3는 **사건 목록과 원인 서술을 함께** 요구할 때 성립한다 — 요구 원소가 2개다 ([design.md](./design.md) D11-4). 이 구분이 없으면 자체 엣지 세트의 X3 케이스가 회귀 세트 `#19`와 반대 처리를 요구하게 된다.

### 요구 형태 미충족 — 개체는 있는데 그 형태만 없다

| ID | 케이스 | 기대 동작 |
|----|--------|----------|
| **X5** | **요구 형태 미충족**: 도구도 맞고 개체도 존재하는데, 요구한 출력 형태의 자료가 없다 | **부분 응답** — "요구 유형의 자료 없음"과 "확인된 인접 사실"을 별도 필드로 분리 반환 (D10) |

X5는 예외가 아니라 **정상 경로**다. 커버리지를 개체가 아니라 **개체 × 형태 격자**로 재면 제품 기술문서는 **10/60**, 고객사 문서는 **30/90** 칸만 차 있다 ([dataset-analysis.md](./dataset-analysis.md) 3장). 빈 칸의 개체도 테이블·그래프에는 전부 있다.

**X5는 `vector_search` 전용이 아니다. 도구 3종 전부에 있다.**

| 도구 | 예 | 상태 | 빈손 케이스 |
|---|---|---|---|
| `vector_search` | "Client-P의 장애 원인은?" | 문서 자산에 **개체 자체가 없다** | T4 |
| `vector_search` | "Product-C1의 API 인증 방식은?" | 문서 자산에 **개체는 있고 형태만 없다** (설치 가이드만 보유) | T4 |
| `knowledge_graph` | "이 직원이 이끄는 프로젝트는?" | 노드는 있고 `LEADS` 엣지만 없다. 소속·담당 고객은 있다 | **T7** |
| `nl2sql` | "Client-X의 진행 중인 프로젝트는?" | `projects` 0행. 계약·매출·티켓은 있다 | T3 |

격자 밀도는 도구마다 다르지만 구조는 같다 — 문서 **10/60**, 그래프 **322/416**, 테이블 **106/120** ([dataset-analysis.md](./dataset-analysis.md) 3장).

원인은 자산 커버리지의 **비대칭**이지만, **분류 축은 요구 출력 형태**다 — D9가 도구 경계를 긋는 축과 같다. "비대칭"은 데이터 성질이지 케이스 유형 이름이 아니다.

X5를 빈손 3종(T3·T4·T7)이나 R1(무매칭)으로 뭉개면 안 된다 — 있는 정보를 버리게 된다. T5(개체 자체가 없음)만은 X5가 아니다. 반대로 인접 사실만 그대로 넘기면 모델이 그로부터 요구된 답을 지어낸다(Q1).

## 카테고리 2 — 라우터 경계

| ID | 케이스 | 기대 동작 |
|----|--------|----------|
| R1 | **무매칭**: 후보 도구 없음 (스몰토크, 데이터 범위 밖 주제) | 도구 호출 없이 구조화 거절 응답 (`out_of_scope`) 반환. 에이전트는 모른다고 답변 (D6) |
| R2 | **애매 매칭**: 후보 복수 | **X3·X4에 해당하면** 병렬 호출 후 병합. X1·X2면 규칙 우선순위로 단일 선택 (D3·D9) |
| R3 | **복수 도구 질문**: 질문이 두 영역에 걸침 (예: 정형 수치 + 문서 근거) | R2와 같은 메커니즘 |
| ~~**R4**~~ | ~~**의존 질문**: 요구 원소끼리 의존한다 (멀티홉)~~ **— 폐기 (2026-08-19)**. 케이스를 세운 두 실물이 **멀티홉이 아니었다**: *"Client-B를 담당하는 직원의 연봉"* 은 `contracts.manager_id JOIN employees.salary` 로 1쿼리이고, *"Client-A가 쓰는 제품의 장애"* 는 `support_tickets.client_id` 로 직접 걸린다. 그래프에서만 2홉이지 테이블에서는 아니다. 게다가 R4와 X4는 **표층도 임베딩도 같아서**(개체 한정어 + 관계 + 서술) 규칙으로 가를 수 없었다 — R4를 독립 상태로 두면 X4를 반드시 깨뜨린다 | X3·X4로 흡수한다. `r4_defined_state` 응답 어휘도 폐기 |
| **R5** | **표층 문자열 충돌**: 스키마의 관계명·컬럼명이 **일반 명사와 겹쳐** 판별이 관계로 오인한다. 실물: `#17` *"고객사 미팅에서 논의된 일정 지연 **이슈**는?"* — `REPORTED_ISSUE`의 "이슈" | 관계 어휘 단독으로 판정하지 않는다 — **개체 한정어가 함께 있을 때만** 관계로 본다. 판별 규칙의 표층 구현 요건 (D9-a) |

**R5는 D12로 해소됐다 — 거절 직전 구제로.** 관계 어휘를 표층으로 세지 않고, **거절 판정에 닿은 질문**(스키마 어휘도 개체 한정어도 없는 질문) 중 문서 최대 유사도가 임계 이상이면 `vector_search`로 보낸다. 자체 엣지 세트의 R5 3문항이 3/3이 됐다 ([design.md](./design.md) D12). 그러나 **게이트에 걸린 질문은 이 구제에 닿지 않는다** — R5 행의 실물 `#17`이 정확히 그 자리에서 틀리고, 틀리게 하는 낱말은 행이 지목한 "이슈"가 아니라 게이트 낱말 `고객사`다 (아래 "미해결 3건의 원인 규명", 이슈 #15). 구제의 자리는 2026-08-27(이슈 #19)에 게이트 미히트 직후에서 거절 직전으로 내려갔고, `#17`의 이 성질은 그대로다.

무매칭(R1)과 애매(R2)는 다르다: 애매는 후보가 **있고** 형태가 상보적인 것, 무매칭은 후보 자체가 **없는** 것. 무매칭에 병렬 폴백을 쓰면 무관한 컨텍스트로 환각을 유발하므로 금지.

**R4를 세운 근거는 무너졌다.** 원래 논거는 *"후보는 있는데 순서가 필요하다"* 였는데, 두 실물 모두 테이블 조인 한 번으로 닿는다는 것이 확인됐다 (위 행). 남은 것은 **개체 한정어가 무시되고 답이 나가는** 형태인데, 그것은 X4가 이미 덮는다 — 개체 한정어 + 서술 요구면 병렬 병합이다. **진짜 멀티홉 질문이 들어오면** 그때 실물을 근거로 다시 세운다. 지금 없는 것에 구조를 만들지 않는다 ([design.md](./design.md) D11-5의 *"실행하지 않을 능력을 만들지 않는다"*).

**R2의 발동 조건은 규칙에 명시된 상보 중복 유형(X3·X4)이다.** 스코어 동률·기준 미달 같은 확신 부족만으로는 병렬하지 않는다 (D3).

## 카테고리 3 — 도구 실패

| ID | 케이스 | 기대 동작 |
|----|--------|----------|
| T1 | nl2sql: LLM이 유효하지 않은 SQL 생성 | 실행 전 검증 실패 → 구조화 에러 반환. 재시도는 실행 오류 메시지를 물려야 하며 횟수는 열린 항목. **빈 응답은 T1이 아니다** — `gemma4:e2b-it-qat`는 숨은 추론 토큰을 뱉어서 `num_predict`가 작으면 빈 문자열을 낸다. 호출 옵션 실수이지 생성 실패가 아니다 ([harness-evaluation.md](./harness-evaluation.md) 2절, `harness/assets/model.json`) |
| T2 | nl2sql: SELECT 외 구문 생성 (INSERT/UPDATE/DDL) | 무조건 차단. 실행 금지, 에러 반환 |
| T3 | nl2sql: 실행 성공, 결과 0행, **접지 검사 통과** | 실패 아님 — "결과 0건"을 정상 응답으로 명시 반환. **다른 자산에 인접 사실이 있으면 X5(부분 응답)로 넘어간다**. 집계 0 한 행 + 검사 통과도 여기가 아니라 `ok` 유지다 — "2억 넘는 계약 몇 건 → 0건"은 정답이다 |
| T4 | vector_search: 전 청크 유사도 임계 미만 / 0건 | "관련 문서 없음" 응답. 저유사도 청크를 억지로 반환하지 않는다. **다른 자산에 인접 사실이 있으면 X5(부분 응답)로 넘어간다** |
| T5 | knowledge_graph: 질문 **개체**가 그래프에 없음 | "개체 없음" 응답. 유사 이름 추측 매칭하지 않는다. **정규화를 어디까지 할지는 열린 항목** |
| **T7** | knowledge_graph: **개체는 있으나 요구한 관계가 없음** (엣지 0건) | T5와 다르다 — 개체가 존재한다. "관계 없음"을 명시 반환하되, **그 개체의 다른 관계나 정형 속성이 있으면 X5(부분 응답)로 넘어간다** |
| **T8** | knowledge_graph: **개체 이름이 여럿을 가리킨다** (동명이인). 실물: `박성민` 2명 — `employee_31` 은 `LEADS` 3개, `employee_4` 는 0개 | **답이 없는 것이 아니라 어느 것인지 모르는 것이다.** T5(부재)와도 T7(관계 부재)과도 다르다. 관계를 합쳐 답하면 **조용히 틀린다**. 후보와 구별 단서를 돌려주고 되묻는다 |
| **T9** | nl2sql: 실행 성공, **빈손**(0행 또는 집계 0/NULL 한 행)인데 **접지 실패 검출**(금액 리터럴이 실측 범위의 ×10 이상 · 문자열이 다른 컬럼에만 있음) | 0행이 "정말 없다"가 아니라 **"질문의 값 조건을 데이터와 대조하지 못했다"** 인 경우다. `isError` 없는 `ungrounded` + `sql`·`hits` 동봉. **X5 승격 금지** (아래). 판정과 근거는 [design.md](./design.md) D18. **한계** — 행이 오는 위장(`미만` + 단위 오류의 전량 반환 · `X3-02`)은 이 검사의 스코프 밖이다: 빈손일 때만 돌기 때문이고, 상시 검사는 #30 으로 이관했다 |
| T6 | 공통: DB 연결 실패 등 인프라 오류 | 데이터 부재(T3~T5·T7·T9)와 구분되는 에러 타입으로 반환 |

**T8 은 도구를 실제로 돌리기 전에는 안 보였다.** 골격이 소재를 **노드 id** 로 고르고 문면이 **이름** 을 쓰는 한,
질문 세트만으로는 드러나지 않는다 — `X5-04` 의 라벨이 그래서 틀렸다 (아래 "알려진 엣지 세트 결함").
T8 을 넣어도 **점수는 그대로다**(엣지 실행 27/29). 라벨이 `partial` 이므로 `ambiguous_entity` 도 오답으로 세어진다.
**점수가 못 보는 개선**이고, 그래서 라벨을 고치지 않고 결함으로 남긴다.

공통 규약: **"도구가 답을 못 냈다"와 "시스템 오류"는 다른 응답 타입**이다. MCP 스펙의 에러 2계층과 대응한다 — 실행 실패(T1·T6)는 `isError: true`, 데이터 부재(T3~T5·T7)·**접지 실패(T9)**·거절(R1)·부분 응답(X5)은 `isError` 없는 정상 결과 + 구조화 필드. 라벨이 "데이터 부재"보다 넓은 것은 T9 때문이다 — 자료는 있는데 질문의 값 조건을 대조하지 못한 상태도 여기 산다. **계층 경계는 그대로다**: 실행이 실패했는가만 위 계층을 가른다.

**빈손 3종(T3·T4·T7)은 전부 X5 승격 후보다.** 도구는 다르지만 구조가 같다 — 요구한 형태의 자료가 없고 다른 자산에 인접 사실이 있는 상태다. 승격하지 않으면 확인된 사실을 버린다. 반대로 T5(개체 자체가 없음)는 승격 대상이 아니다 — 인접 사실도 없다.

**T9 는 빈손 모양이지만 승격 후보가 아니다.** 자료가 **있으므로** X5 정의("요구한 형태의 자료가 없다")에 안 맞고, 없는 것은 자료가 아니라 질문의 값 조건과 데이터의 대조다. 여기에 인접 사실을 얹으면 모델이 그것을 요구된 답으로 쓴다 (Q1) — "8000만원 이상 받는 직원"에 연봉 범위 3736~9520을 붙이면 그 수치가 답으로 나간다.

  안 돌아오고(반증), 게이트 낱말만 벗기면 구제가 살아나 정답이 된다. **셋 중 유일하게 구조
  원인이 잡힌 문항**이다 — R5 구제가 게이트에 걸리지 않은 질문에만 작동한다는 규칙 구조가 원인이다.
- **#25 — `이슈`는 오히려 정답 쪽으로 당긴다.** `이슈`→`요청` 치환 시 graph 점수가 0.4171 → 0.3954로
  떨어진다(`REPORTED_ISSUE` 어휘라 당연하다). 원인은 최상급 관계 집계 문형(*"~가 가장 많은 제품은?"*)이
  graph 시그니처보다 vector 시그니처에 0.0135 가깝다는 것. 게이트를 벗기면 maxdoc 0.4535 < 0.52 라
  거절로 더 나빠진다.

공통으로 남는 관찰은 가설과 다른 층에 있다: **셋 다 argmax 마진 ≤ 0.019의 근소 동률에서 진다.**
이것은 어휘 충돌이 아니라 시그니처 임베딩의 해상도 문제이고, 개별 실패라는 판정을 바꾸지 않는다.

**충돌 어휘 유형의 엣지 세트 커버리지** (가설이 맞았다면 세기로 했던 것 — 반증됐지만 판단 재료로 남긴다).
충돌 어휘는 질문에서 역산하지 않고 자산에서 정의했다: SQL 어휘(`surface-gate.json` 테이블 표층형 +
저카디널리티 값) ∪ 그래프 어휘(관계 7종 + 타입 표층형, `tools.py`) 중 {SQL, 그래프, 문서 제목·헤딩} 두
자산군 이상에 걸리는 낱말 — **13어** (고객 · 고객사 · 관리 · 담당 · 도입 · 부서 · 부서장 · 사원 · 이슈 · 장애 ·

제목·헤딩으로 좁혔다 — 이것이 이 정의의 한계다.

  지나는 조합은 이미 두껍게 커버돼 있고, 단일 도구 기대 12문항 중 **11이 통과**한다 (실패 1건 `X5-05`는

  오선택은 아니다** — 가설 반증과 정합한다.
- **#17형 — 게이트 히트인데 기대가 `vector_search` 단독 — 은 0/29. 사각지대다.** R5 라벨 3문항 중

  `nl2sql`이다. 문항 보강은 이 이슈에서 하지 않는다 — 수정 착수를 판단한 뒤 후속으로 채운다.

**고칠지의 별도 판단에 넘기는 재료**: ① #17은 구조 원인이라 고치는 방향이 보인다 — 게이트 히트여도

히트 × 문서 의도)만 대상으로 하되 그 유형의 엣지 문항 보강이 선행돼야 하고, #6·#25는 알려진 불일치로
둔다.** 재현은 위 표의 문장을 `harness/build/router.py` 의 `route()`/`embed()` 에 그대로 넣으면 된다.

### 알려진 엣지 세트 결함 — `X5-04`

`X5-04`(*"박성민 님이 현재 어떤 프로젝트를 맡고 계신가요?"*)의 라벨 `partial`(T7)은 **틀렸다.**

알려진 불일치로 기록하고 예외 규칙을 넣지 않는다.

유형이 있다는 증거이고, 소재 선택 규칙이 *id* 로 고르고 문면이 *이름* 을 쓸 때 생기는 함정이다.
