# 설계 결정 — Company-X MCP 검색 시스템

> 과제 원문 요구는 [requirements.md](./requirements.md), 용어는 [/CONTEXT.md](../CONTEXT.md), 데이터 실측은 [dataset-analysis.md](./dataset-analysis.md), 각 결정을 뒷받침하는 관련 연구는 [references/related-work.md](./references/related-work.md) 참조.
> 이 문서는 **우리 팀이 내린 결정**과 그 이유, 아직 열어둔 항목을 기록한다.

## 아키텍처 한 장

> **라우터 배치는 공통부 구현 후 재평가로 미뤄져 있다.** 아래 A/B 중 선택 필요 — 비교는 [routing-topology.md](./routing-topology.md), 항목은 "열어둔 항목"의 **라우터 배치**.

**A안 — 게이트웨이형** (라우터가 도구를 직접 실행하고 결과까지 반환, MCP 왕복 1회)

```
사용자 질문
   ↓
AI 에이전트 (Ollama 소형 LLM)
   ↓  MCP 호출: ask(question)          ← 왕복 1회
MCP 서버 ─ 등록 도구 4개
   ├─ ask            ← 게이트웨이 (규칙 기반 라우터 내장)
   │    ├─ 규칙 매칭 확실 → 도구 1개 호출
   │    └─ 상보 중복(X3·X4) → 후보 도구 병렬 호출 후 병합
   ├─ vector_search  ← 직접 호출도 가능 (검증·시연용)
   ├─ nl2sql
   └─ knowledge_graph
   ↓
PostgreSQL (+ pgvector)   ← 문서 청크·정형 테이블·그래프 전부 여기
   ↓
에이전트 LLM이 반환 컨텍스트로 최종 답변 생성
```

**B안 — 조언자형** (라우터는 어느 도구를 쓸지만 알려주고, 에이전트가 그 도구를 호출, MCP 왕복 2회)

```
사용자 질문
   ↓
AI 에이전트 (Ollama 소형 LLM)
   ↓  ① route(question)                ← 왕복 1
MCP 서버 ─ route: 규칙 판별만 수행
   ↓  {tool:"nl2sql", args:{...}, confidence:0.9}  또는  {out_of_scope}
에이전트 (지시대로 호출 — 코드가 실행하는 B2 권장, LLM이 고르는 B1은 비권장)
   ↓  ② nl2sql(args)                   ← 왕복 2
MCP 서버 ─ 도구 3종 (실사용 경로)
   ↓
PostgreSQL (+ pgvector)
   ↓
에이전트 LLM이 결과로 최종 답변 생성
```

## 확정 결정

### D1. 라우터는 MCP 서버 측 도구다 (배치 형태는 미확정)

라우터를 **에이전트 밖, MCP 도구로 둔다**는 것까지는 확정이다. 규칙 기반 판별 로직이 MCP 서버에 있고 에이전트에는 없다.

- **이유**: 데이터셋 README의 도구 매핑 표가 라우터를 "MCP 도구"로 표기한다. 소형 LLM에게 도구 선택을 맡기지 않는다는 요건(과제의 "규칙 기반" 문면)도 이 배치로 충족된다.
- **기각한 대안**: 라우터를 MCP 밖 에이전트 측 모듈로 두기 (README 표기와 어긋남), LLM 도구 선택 + 규칙 폴백 ("규칙 기반" 문면과 어긋남).
- **미확정 부분**: 그 라우터가 **도구를 직접 실행하는지(A안)**, **어느 도구를 쓸지만 알려주는지(B안)**. 두 안 모두 위 확정 사항을 만족한다. 비교는 [routing-topology.md](./routing-topology.md) — 핵심 트레이드오프는 *A안의 복잡도 집중* 대 *B안의 판단 가시성*이다.
- **결정 시점을 공통부 구현 이후로 미룬다** (2026-08-12). D3·D7·D9·D10은 **전부 A/B와 무관**하고, 도구 3종 핸들러·규칙 판별 함수·부분 응답 스키마도 두 안에서 동일하다 — 이것이 작업량의 대부분이다. 반면 A/B 선택의 핵심 입력 두 가지(**병렬 호출이 실제로 얼마나 자주 발동하는지**, **부분 응답 조립이 얼마나 복잡한지**)는 만들어 봐야 알 수 있다. 지금 닫으면 정보 없이 닫는 것이고, 미루는 비용은 0이다.
- **재평가 시점**: 공통부(도구 3종 + 판별 함수 + 부분 응답 스키마) 완성 및 라우팅 축 29/30 확인 직후, 에이전트 착수 **전**.

### D2. 등록 도구는 4개 — `ask` + 3종

라우터 도구(`ask` 또는 `route`) + `vector_search`, `nl2sql`, `knowledge_graph` 전부 MCP 도구로 등록. **총 4개라는 점은 D1의 A/B 선택과 무관하게 확정**이다.

- **A안이면**: 에이전트는 평소 `ask`만 호출하고, 3종은 개별 검증·시연·심사용 창구다.
- **B안이면**: 3종이 에이전트의 **실사용 호출 경로**가 된다. 등록 명분이 더 분명해진다.

- **이유**: 블로그 문면 "3개의 MCP 도구를 구현합니다"와 README 표(라우터 포함 4개를 MCP 도구로 표기)를 동시에 충족. `ask`만 노출하면 도구 3종 구현 요구 미충족으로 해석될 심사 리스크.
- 도구 식별자는 questions.json의 `tool` 값(`nl2sql`, `vector_search`, `knowledge_graph`)과 일치시킨다.
- **부수 효과 — 에이전트 입장에서 선택지가 1개다**: 에이전트는 도구 선택 문제를 겪지 않는다. Mem2ActBench(arXiv:2601.19935) Table 5는 후보 도구 수가 1→2→5로 늘 때 hard negative 조건에서 선택 정확도가 94.5%→78.0%→69.75%로 떨어짐을 보인다. **다만 같은 실험에서 random negative는 무변화(93.5~95.5%)였다 — 원인은 개수 자체가 아니라 의미적으로 겹치는 후보의 존재다.**
  - **인용 형태**: 개별 점(69.75%)이 아니라 **같은 후보 수에서 hard와 random이 24.75%p 벌어졌다는 대조**를 쓴다. 개별 점은 반복 실행 분산 안에 들어가지만(Bhat et al. 2026 — 최대 18.9%p), 같은 실험 안의 대조는 그 노이즈가 상쇄된다.
- **부수 효과의 성립 조건**: **A안**(에이전트가 `ask`만 호출 — 후보 1개) 또는 **B2**(코드가 `route` 결과를 집행 — LLM이 선택을 아예 안 함)에서만 성립한다. **B1**(LLM이 `route` 결과를 읽고 도구를 고름)이면 후보 4개 hard negative 조건으로 되돌아간다 — B1 비권장 근거다 ([routing-topology.md](./routing-topology.md) 3.6).
  - **강제 수단은 프로토콜이 아니다.** 도구 4개를 등록하면 `tools/list`에 4개가 전부 노출되고, MCP 서버는 클라이언트가 무엇을 호출할지 막을 수 없다. "`ask`만 호출한다"는 **에이전트 코드에 하드코딩**해야 하며, 시스템 프롬프트 지시로 두면 소형 LLM에서 샌다. **에이전트 착수 시 요건**이고, 새는지 여부는 검증 항목이다 (edge-cases.md **Q4**).

- **자산 겹침과의 관계**: 실측 결과 지식 그래프는 정형 테이블에서 100% 도출되고(관계 7종 전부 집합 일치), 문서 40건은 전부 그래프 개체를 언급하며, `support_tickets`의 title 28종 중 18종이 문서와 주제가 겹친다 ([dataset-analysis.md](./dataset-analysis.md)) — **우리 도구 3종은 hard negative 관계이고, 이 데이터셋에서 자산을 겹치지 않게 설계하는 선택지는 없다.** 따라서 방어선은 도구 선택을 LLM에게 맡기지 않는 것(D1) 하나이며, 겹침 자체는 규칙 라우터의 판별 기준(D9)과 중복 구간 처리(D3)로 다룬다.

### D3. 병렬 정책 — 기본 단일, **상보 중복 구간에서만** 병렬

규칙 매칭이 확실하면 도구 1개만 호출. 병렬은 **확신 부족으로 발동하지 않고**, 라우터 규칙에 명시된 **상보 중복 유형**(edge-cases.md **X3·X4**)에 해당할 때만 발동한다.

| 중복 유형 | 두 도구의 답 | 처리 |
|---|---|---|
| **X1** 관계를 세는 집계 / **X2** 관계를 따라가는 조회 | **같다** — 그래프가 테이블의 파생이므로 | **단일 선택** (D9 규칙 3·4) |
| **X3** 사건 조회 / **X4** 개체 지목 서술 | **다르다** — 티켓은 사건 *목록*, 문서는 원인 *서술* | **병렬 호출 후 병합** |

**병렬 호출을 누가 수행하는지는 D1의 A/B 선택에 종속된다** — A안이면 `ask` 내부에서, B안이면 `route`가 후보 목록을 반환하고 에이전트가 호출한다. 발동 조건 자체는 두 안 모두 동일하다.

- **이유**: 병렬 호출은 과제 요구가 아니라 우리 설계 선택이다 — 출처 3곳과 데이터셋 전수 검사에서 "병렬"은 0회, "Parallel"은 요강의 괄호 별칭 1회뿐이고 어느 출처도 정의하지 않으며, questions.json 30개는 `tool`이 배열이 아니라 문자열이라 기대 출력이 도구 1개다 ([dataset-analysis.md](./dataset-analysis.md) 6장). 병렬을 쓰는 근거는 문면이 아니라 **자산 중복 실측**이다 — 상보 중복 구간에서는 한 도구만으로 답이 완성되지 않는다. 반대로 동일 중복 구간에 병렬을 걸면 같은 답을 두 번 받아 토큰만 2배가 되고, Pylon-7의 L2.5 ablation(중복·무관 컨텍스트 추가가 정확도를 떨어뜨림)에 정면으로 걸린다.
- **부수 효과**: "왜 병렬을 했는가"뿐 아니라 **"왜 X1·X2에는 병렬을 안 했는가"**도 데이터로 설명된다.
- **주의**: 라우터 규칙을 questions.json 30개에 과적합시키지 않는다. 30개는 검증용이지 학습용이 아니다.

### D4. NL2SQL — 도구 내부에서 LLM이 SQL 생성

`nl2sql` 도구가 Ollama를 호출해 스키마 + 질문 프롬프트로 SQL을 생성하고, 실행 후 결과를 반환한다. SELECT만 허용.

- **이유**: 라우터는 도구에 자연어 질문을 넘기므로(A안·B안 공통) SQL 변환은 `nl2sql` 도구 내부에서 일어나야 함. 규칙/템플릿 변환은 데이터셋 과적합이라 배제(팀 방침).

### D5. 지식 그래프 — PostgreSQL 테이블 + 재귀 CTE

nodes.json/edges.json을 PostgreSQL 테이블(nodes, edges)로 적재하고, 다단계 관계 탐색은 recursive CTE로 구현.

- **이유**: 과제 흐름도상 모든 도구가 PostgreSQL로 향함. "PostgreSQL 기반 지능형 데이터 플랫폼" 취지 부합, 추가 인프라 없음. Apache AGE는 RAM 4GB 제약에 부담, 인메모리 JSON은 플랫폼 그림에서 벗어남.
- "온톨로지 기반" 요구는 그래프 스키마 문서(노드 5유형, 관계 7종)를 온톨로지 정의로 명시하는 것으로 대응.

### D6. 무매칭 질문은 정직한 거절

라우터에 후보 도구가 없는 질문(스몰토크, 데이터 범위 밖)은 도구를 호출하지 않고 구조화 거절 응답(`out_of_scope`)을 반환한다. 에이전트는 이를 받아 모른다고 답변한다.

- **이유**: 무관한 컨텍스트를 소형 LLM에 주면 환각 유발. **애매**(후보 있음, 상보 중복 구간 → D3 병렬)와 **무매칭**(후보 없음 → 거절)은 다른 케이스.
- **기각한 대안**: 무매칭 시 전 도구 병렬 폴백 (스몰토크에 DB 3회 조회 + 환각 위험), 최근접 도구 강제 라우팅.

### D7. 엣지케이스는 구조 레벨만 분석, 검증은 이원화

엣지케이스 분석은 **구조 레벨**(데이터셋 내용과 무관한 시스템 실패 유형)만 허용하고, 인스턴스 레벨(개별 질문·문서에 맞춘 튜닝)은 금지한다. 검증 세트는 둘로 나눈다: 자체 작성 엣지 세트(케이스 유형별) + questions.json(회귀 전용, 규칙 튜닝 사용 금지).

**경계선** — "분석"과 "튜닝"을 구분한다:

| | 허용/금지 |
|---|---|
| **자산 간 구조를 대조**한다 — 무엇이 어디에 중복되는가, 그래프가 테이블에서 도출되는가 | ✅ **허용.** 데이터셋 인스턴스가 아니라 스키마·자산 관계를 보는 일이다 |
| 개별 질문에서 **키워드·규칙을 역산**한다 | ❌ 금지 |
| 특정 질문을 맞추려고 **예외 규칙**을 넣는다 | ❌ 금지 (#5 처리 참조) |

열린 항목을 닫기 전에는 **문헌보다 먼저 데이터셋을 대조한다** ([reading-priority.md](./reading-priority.md) 티어 3).

**회귀는 2축으로 잰다** — questions.json의 결함 2건은 성격이 다르다.

| 축 | 기대값 | 근거 |
|---|---|---|
| **라우팅 축** — 고른 도구가 기대 도구와 같은가 | **29/30** | #5는 #25·#29와 구조가 같은데 배정이 반대다. 원칙적 규칙으로 셋 동시 만족 불가 → **알려진 불일치로 문서화**하고 예외 규칙을 넣지 않는다 |
| **실행 축** — 선택된 도구가 올바른 응답 *유형*을 내는가 | **30/30** | #23("서울물산")은 존재하지 않는 개체명이다. **정답을 "결과 반환"이 아니라 "개체 부재(T5) 응답"으로 재정의**한다 → 실패 케이스가 아니라 T5 검증 실물이 된다 |

- **이유**: 엣지 견고성과 과적합 방지 동시 충족. 30개가 전부 정상 매칭 질문은 아니지만(#23이 반례), 엣지 케이스는 거의 없으므로 자체 세트가 여전히 필요하다.
- **#5를 맞추지 않는 이유**: 30/30을 만들려면 "프로젝트 수는 nl2sql, 고객 수는 knowledge_graph"라는 근거 없는 예외가 규칙에 들어간다. 이건 이 조항이 금지하는 인스턴스 과적합이고, 자체 엣지 세트에서 같은 유형이 나오면 무너진다.
- 케이스 카탈로그: [edge-cases.md](./edge-cases.md) (자산 중복 / 라우터 경계 / 도구 실패 / 응답 품질 4개 카테고리).

### D8. 구현 스택 — 공식 MCP SDK 직접 사용 (air 미채택)

TypeScript + `@modelcontextprotocol/sdk` 1.30.0. 주최사 권장 프레임워크인 air(`@airmcp-dev/core` 0.3.0)는 채택하지 않는다. 프로토콜 리비전은 SDK가 지원하는 최신인 **`2025-11-25`**.

- **이유**: air 채택을 정당화하던 유일한 실질 기능은 **7-Layer Meter**(필수 참조 [2] Pylon-7의 계층을 계측)였는데, **실측에서 동작하지 않음을 확인했다.** `defineTool`에 `layer`를 명시해도 `meter-middleware.js`의 `classify()`가 도구 이름·파라미터만 보고 `layer` 속성을 무시한다(타입과 공식 문서에는 있는데 구현에 없다). 자동 분류 규칙도 완전 일치 정규식이라 우리 도구명이 하나도 걸리지 않아 모든 호출이 L4로 뭉개진다. 검증 상세는 [air-evaluation.md](./air-evaluation.md) 8절
- 도구가 4개뿐이라 보일러플레이트 절감은 결정 근거가 되지 못하고, 플러그인 19종 중 우리에게 맞는 것은 timeout·dedup 둘뿐이다(`retryPlugin`은 T1 제약과 충돌).
- 과제 문서가 air를 **"사용 의무는 없습니다"**로 명시하므로 미채택에 규정 위반은 없다. air를 검토하고 근거를 들어 기각한 기록 자체가 심사 서술이 된다.
- **기각으로 잃는 것과 대안**: Pylon-7 계층 계측은 포기하지 않는다. 도구 핸들러를 감싸는 얇은 래퍼에서 계층을 상수로 붙여 기록하며, air의 이름 패턴 추측보다 논문 계층 정의에 맞춰 우리가 명시하는 편이 정확하다 — `ask` = L5 Routing, 도구 3종 = L3 Resource.
- **부수 확인**: SDK 1.30.0의 `LATEST_PROTOCOL_VERSION`이 `2025-11-25`라, 스펙 문서상 최신인 2026-07-28 리비전은 **어떤 스택을 골라도 구현할 수 없다**. air의 리스크가 아니라 생태계 상태였다 ([mcp-spec.md](./references/mcp-spec.md) 참조).

### D9. 도구 경계는 "요구 출력 형태"로 가른다 (데이터 자산이 아니라)

라우터는 **질문이 어느 자산에 있는가**가 아니라 **어떤 형태의 답을 요구하는가**로 판별한다.

| # | 규칙 | 도구 |
|---|---|---|
| 1 | **서술**을 요구 — 원인, 방법, 절차, 내용, 결정, 제안 | `vector_search` |
| 2 | **정형 속성·수치 값**을 요구 — 금액, 연봉, 기간, 상태, 행 개수 | `nl2sql` |
| 3 | **개체 식별·연결**을 요구 — 누가/무엇을/어디 소속/담당 | `knowledge_graph` |
| 4 | **관계를 세는 집계** — 세는 대상이 관계이므로 규칙 3에 귀속 | `knowledge_graph` |

- **이유**: 자산 기준("각 도구는 하나의 데이터 자산에 대응")은 이 데이터셋에서 성립하지 않는다 — 그래프는 테이블에서 100% 도출되고, 문서 40건은 전부 그래프 개체를 언급하며, 티켓 title 28종 중 18종이 문서와 주제가 겹친다 ([dataset-analysis.md](./dataset-analysis.md)). 자산으로 가르면 겹치는 구간에서 규칙이 정의되지 않는다.
- **검증**: 이 규칙을 questions.json 30개에 **대조**한 결과 **29/30 일치** (vector_search 10/10, nl2sql 9/10, knowledge_graph 10/10). 유일한 불일치 #5는 데이터셋 내부 비일관성이다 (D7 회귀 2축).
  - 규칙 4를 뒤집으면 #25·#29 두 건이 대신 틀린다(28/30). **29/30이 원칙적 규칙의 상한**이다.
- **동일 중복(X1·X2) 처리**: 규칙 3·4가 우선순위 역할을 한다 — 관계만 물으면 `knowledge_graph`, 정형 속성이 함께 걸리면 `nl2sql`.
- **도구 설명(description)도 이 축으로 쓴다.** 자산으로 설명하면 설명끼리 겹쳐 hard negative가 된다 (Hasan et al. 2026 — compact하고 목적이 분명한 설명).

### D10. 부분 응답 — 요구 형태 미충족을 구조화해 반환

질문이 요구한 출력 형태를 담은 자산에 자료가 없고 **다른 자산에 인접 사실만 있을 때**, 응답은 **"요구 유형의 자료 없음"과 "확인된 인접 사실"을 별도 필드로 분리**해 반환한다.

```jsonc
{
  "status": "partial",
  "requested_form": "narrative",
  "unavailable": { "asset": "documents", "reason": "no_document_for_entity" },
  "adjacent_facts": { "source": "knowledge_graph", "data": [ /* ... */ ] }
}
```

- **왜 필요한가**: 문서는 고객사 **15/30**, 제품 **10/12**만 커버하는데 나머지 개체도 테이블·그래프에는 전부 있다. 즉 `"Client-P의 장애 원인은?"` 같은 질문이 **상시** 이 상태에 빠진다. 예외가 아니라 정상 경로다.
- **그냥 인접 사실만 넘기면 안 되는 이유**: 원인을 물었는데 "이슈가 있었다"는 사실만 주면 소형 LLM이 그로부터 원인을 지어낸다 — Q1(환각)이 발생하는 정확한 지점이다. 응답만 보고는 모델이 "원인"인지 "인접 사실"인지 구분할 수 없다.
- **거절(D6)과 다르다**: 거절은 후보 도구가 없는 것, 부분 응답은 **도구도 맞고 개체도 있는데 요구 형태만 없는 것**이다. MCP 스펙상 둘 다 `isError` 없는 정상 결과이고 `structuredContent`로 구분한다.
- **에이전트 규약**: 부분 응답을 받으면 인접 사실을 요구된 답인 것처럼 말하지 않는다. *"원인 기록은 없습니다. 다만 …한 기록은 있습니다."*
- **기각한 대안**: 요구 형태 미충족 시 전면 거절 (고객사 절반이 이 경로라 시스템이 자주 "모른다"고 답함), 있는 것만 그대로 반환 (Q1 환각 위험 그대로).

## 도구별 실제 예시 (questions.json 기반)

| 질문 | D9 규칙 | 라우터 선택 | 처리 |
|------|---|-----------|------|
| "서울 지역 매출 상위 5개 고객사를 알려줘" | 2 (수치) | `nl2sql` | LLM이 SQL 생성 (sales+clients 조인, region='서울', GROUP BY, LIMIT 5) → 실행 → 행 반환 |
| "최근 서버 장애 사례와 원인을 알려줘" | 1 (서술) | `vector_search` | 질문 임베딩 → document_chunks 유사도 검색 → 상위 청크 반환 |
| "Client-A가 사용 중인 제품 목록은?" | 3 (개체 연결) | `knowledge_graph` | client 노드에서 `USES` 엣지 탐색 → 제품 노드 목록 반환 |

중복 구간 예시 (questions.json에는 없는 유형 — 자체 엣지 세트 대상):

| 질문 | 유형 | 처리 |
|------|---|------|
| "SSL 인증서 관련 장애가 있었고 원인이 뭐야?" | **X3** 상보 중복 | `nl2sql`(티켓 목록) + `vector_search`(원인 서술) **병렬 → 병합** |
| "가장 많은 고객을 담당하는 직원은?" | **X1** 동일 중복 | `knowledge_graph` **단일** (D9 규칙 4). 병렬하면 같은 답이 두 번 |
| "Client-P의 장애 원인은?" (문서 미커버 고객사) | **X5** 요구 형태 미충족 | `vector_search` 빈손 + 그래프에 이슈 사실 있음 → **부분 응답** (D10) |
| "Product-C1의 API 인증 방식은?" (커버된 제품, 없는 형태) | **X5** 요구 형태 미충족 | Product-C1은 설치 가이드만 보유 — 문서 자산에 **개체는 있고 형태만 없다.** `vector_search` 빈손 + 그래프·테이블에 제품 사실 있음 → **부분 응답** (D10) |

라우터가 도구 결과를 컨텍스트로 반환하면 에이전트 LLM이 최종 답변 문장을 생성한다. (반환 주체가 `ask`인지 `route`+도구인지는 D1의 A/B에 종속 — 위 표는 두 안 모두 동일하다.)
