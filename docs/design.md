# 설계 결정 — Company-X MCP 검색 시스템

> 과제 원문 요구는 [requirements.md](./requirements.md), 용어는 [/CONTEXT.md](../CONTEXT.md), 데이터 실측은 [dataset-analysis.md](./dataset-analysis.md), 각 결정을 뒷받침하는 관련 연구는 [references/related-work.md](./references/related-work.md) 참조.
> 이 문서는 **우리 팀이 내린 결정**과 그 이유, 아직 열어둔 항목을 기록한다.

## 아키텍처 한 장

> **라우터 배치는 게이트웨이형으로 확정됐다** (2026-08-21). 기각한 조언자형과의 비교·근거는
> [routing-topology.md](./routing-topology.md), 결정 기록은 그 문서 5절.

```
사용자 질문
   ↓
AI 에이전트 (Ollama 소형 LLM)
   ↓  MCP 호출: ask(question)          ← 왕복 1회
MCP 서버 ─ 등록 도구 4개
   ├─ ask            ← 게이트웨이 (규칙 기반 라우터 내장)
   │    ├─ 규칙 매칭 확실 → 도구 1개 호출
   │    ├─ 요구 원소 둘(X3·X4) → 후보 병렬 호출 → 둘 다 내용 있으면 병합
   │    └─ 응답에 routed_to · matched_rule · why 를 함께 실어 보낸다 (의무)
   ├─ vector_search  ← 직접 호출도 가능 (검증·시연용)
   ├─ nl2sql
   └─ knowledge_graph
   ↓
PostgreSQL (+ pgvector)   ← 문서 청크·정형 테이블·그래프 전부 여기
   ↓
에이전트 LLM이 반환 컨텍스트로 최종 답변 생성
```

## 확정 결정

### D1. 라우터는 MCP 서버 측 도구다 — **게이트웨이형(A안) 확정**

라우터를 **에이전트 밖, MCP 도구로 둔다**는 것까지는 확정이다. 규칙 기반 판별 로직이 MCP 서버에 있고 에이전트에는 없다.

- **이유**: 데이터셋 README의 도구 매핑 표가 라우터를 "MCP 도구"로 표기한다. 소형 LLM에게 도구 선택을 맡기지 않는다는 요건(과제의 "규칙 기반" 문면)도 이 배치로 충족된다.
- **기각한 대안**: 라우터를 MCP 밖 에이전트 측 모듈로 두기 (README 표기와 어긋남), LLM 도구 선택 + 규칙 폴백 ("규칙 기반" 문면과 어긋남).
- **배치 확정 (2026-08-21)**: **A안 — 게이트웨이형.** 라우터 도구 `ask` 가 판별·실행·병합까지 하고 결과를 돌려준다. MCP 왕복 1회.
  - 2026-08-12 이 "만들어 봐야 안다"고 한 입력 둘은 **A안 쪽이었으나 결정적이지 않았다** — 병렬 발동률 6.7%(현실 분포), 부분 응답 조립은 도구 안에서 끝난다.
  - **가른 것은 확장 가능성이다.** 새 응답 상태 하나(`ambiguous_entity`)를 넣는 데 A안 1파일 1줄, B안 2파일 10줄이다. `route` 는 도구를 실행하지 않아 상태를 미리 알 수 없으므로, 새 상태마다 예고와 에이전트 처리가 함께 늘어난다 — 구조적 차이다. 그리고 이 프로젝트는 응답 상태가 계속 늘어난다.
  - **의무 조항**: `ask` 응답의 `structuredContent` 에 `routed_to`·`matched_rule`·`why` 를 반드시 싣는다. A안이 파는 관측성을 회수하는 값싼 수단이다 ([routing-topology.md](./routing-topology.md) 4.4).
  - 근거 전문과 실측은 [routing-topology.md](./routing-topology.md) 4.7·5.
- **결정 시점을 공통부 구현 이후로 미룬다** (2026-08-12). D3·D7·D9·D10은 **전부 A/B와 무관**하고, 도구 3종 핸들러·규칙 판별 함수·부분 응답 스키마도 두 안에서 동일하다 — 이것이 작업량의 대부분이다. 반면 A/B 선택의 핵심 입력 두 가지(**병렬 호출이 실제로 얼마나 자주 발동하는지**, **부분 응답 조립이 얼마나 복잡한지**)는 만들어 봐야 알 수 있다. 지금 닫으면 정보 없이 닫는 것이고, 미루는 비용은 0이다.
- **재평가 시점**: 공통부(도구 3종 + 판별 함수 + 부분 응답 스키마) 완성 및 라우팅 축 29/30 확인 직후, 에이전트 착수 **전**.

### D2. 등록 도구는 4개 — `ask` + 3종

라우터 도구(`ask` 또는 `route`) + `vector_search`, `nl2sql`, `knowledge_graph` 전부 MCP 도구로 등록. **총 4개라는 점은 D1의 A/B 선택과 무관하게 확정**이다.

- **A안이면**: 에이전트는 평소 `ask`만 호출하고, 3종은 개별 검증·시연·심사용 창구다.
- **B안이면**: 3종이 에이전트의 **실사용 호출 경로**가 된다. 등록 명분이 더 분명해진다.

- **이유**: 블로그 문면 "3개의 MCP 도구를 구현합니다"와 README 표(라우터 포함 4개를 MCP 도구로 표기)를 동시에 충족. `ask`만 노출하면 도구 3종 구현 요구 미충족으로 해석될 심사 리스크.
- 도구 식별자는 questions.json의 `tool` 값(`nl2sql`, `vector_search`, `knowledge_graph`)과 일치시킨다.
- **부수 효과 — 에이전트 입장에서 선택지가 1개다**: 에이전트는 도구 선택 문제를 겪지 않는다. Mem2ActBench(arXiv:2601.19935) Table 5는 후보 도구 수가 1→2→5로 늘 때 hard negative 조건에서 선택 정확도가 94.5%→78.0%→69.75%로 떨어짐을 보인다. **다만 같은 실험에서 random negative는 무변화(93.5~95.5%)였다 — 원인은 개수 자체가 아니라 의미적으로 겹치는 후보의 존재다.**
  - **인용 형태**: 개별 점(69.75%)이 아니라 **같은 후보 수에서 hard와 random이 24.75%p 벌어졌다는 대조**를 쓴다. 개별 점은 반복 실행 분산 안에 들어가지만(Bhat et al. 2026 — 최대 18.9%p), 같은 실험 안의 대조는 그 노이즈가 상쇄된다.
- **부수 효과의 성립 조건**: **A안**(에이전트가 `ask`만 호출 — 후보 1개) 또는 **B2**(코드가 `route` 결과를 집행 — LLM이 선택을 아예 안 함)에서만 성립한다. **B1**(LLM이 `route` 결과를 읽고 도구를 고름)이면 후보 4개 hard negative 조건으로 되돌아간다 — B1 비권장 근거다 ([routing-topology.md](./routing-topology.md) 3.6).
  - **강제 수단은 프로토콜이 아니다.** 도구 4개를 등록하면 `tools/list`에 4개가 전부 노출되고, MCP 서버는 클라이언트가 무엇을 호출할지 막을 수 없다. "`ask`만 호출한다"는 **에이전트 코드에 하드코딩**해야 하며, 시스템 프롬프트 지시로 두면 소형 LLM에서 샌다. **에이전트 착수 시 요건**이고, 새는지 여부는 검증 항목이다 (edge-cases.md **Q4**).

- **자산 겹침과의 관계**: 실측 결과 지식 그래프는 정형 테이블에서 100% 도출되고(관계 7종 전부 집합 일치), 문서 40건은 전부 그래프 개체를 언급하며, `support_tickets`의 title 28종 중 18종이 문서와 주제가 겹친다 ([dataset-analysis.md](./dataset-analysis.md)) — **자산 축에서 우리 도구 3종은 hard negative 관계이고, 이 데이터셋에서 자산을 겹치지 않게 설계하는 선택지는 없다.**

**다만 방어선은 둘이다.**

| 방어선 | 무엇을 하나 |
|---|---|
| **D1** — 도구 선택을 LLM에게 맡기지 않는다 | 선택 문제를 **회피**한다 |
| **D9** — 도구를 자산이 아니라 요구 출력 형태로 가른다 | 겹침 자체를 **줄인다** |

D9가 핵심이다. **형태 축에서 도구 3종은 hard negative가 아니라 거의 배타적이다** — 규칙 4개가 29/30을 맞춘다. 겹치는 구간(X3·X4)조차 모호함이 아니라 **두 형태를 동시에 요구하는** 명확한 상태이고, 그래서 병렬 병합으로 처리된다(D3). 자산으로 도구 설명을 쓰면 설명끼리 겹쳐 hard negative를 우리 손으로 만드는 셈이다(D9 마지막 항).

즉 "겹치니까 LLM에게 안 맡긴다"가 아니라 **"자산이 아니라 형태로 갈라서 설명이 겹치지 않게 설계했고, 선택도 LLM에게 맡기지 않는다"**가 정확한 서술이다.

### D3. 병렬 정책 — 기본 단일, **상보 중복 구간에서만** 병렬

규칙 매칭이 확실하면 도구 1개만 호출. 병렬은 **확신 부족으로 발동하지 않고**, 라우터 규칙에 명시된 **상보 중복 유형**(edge-cases.md **X3·X4**)에 해당할 때만 발동한다.

| 중복 유형 | 두 도구의 답 | 처리 |
|---|---|---|
| **X1** 관계를 세는 집계 / **X2** 관계를 따라가는 조회 | **같다** — 그래프가 테이블의 파생이므로 | **단일 선택** (D9 규칙 3·4) |
| **X3** 사건 조회 / **X4** 개체 지목 서술 | **다르다** — 티켓은 사건 *목록*, 문서는 원인 *서술* | **병렬 호출 후 병합** |

**병렬 호출은 `ask` 내부에서 수행한다** (D1 A안 확정, 2026-08-21). 판정은 2단계다 — 접속 탐지로 요구 원소가 둘인지 보고, 후보 둘을 실제로 태워 둘 다 `ok` 일 때만 병렬로 굳힌다.

- **이유**: 병렬 호출은 과제 요구가 아니라 우리 설계 선택이다 — 출처 3곳과 데이터셋 전수 검사에서 "병렬"은 0회, "Parallel"은 요강의 괄호 별칭 1회뿐이고 어느 출처도 정의하지 않으며, questions.json 30개는 `tool`이 배열이 아니라 문자열이라 기대 출력이 도구 1개다 ([dataset-analysis.md](./dataset-analysis.md) 6장). 병렬을 쓰는 근거는 문면이 아니라 **자산 중복 실측**이다 — 상보 중복 구간에서는 한 도구만으로 답이 완성되지 않는다. 반대로 동일 중복 구간에 병렬을 걸면 같은 답을 두 번 받아 토큰만 2배가 되고, Pylon-7의 L2.5 ablation(중복·무관 컨텍스트 추가가 정확도를 떨어뜨림)에 정면으로 걸린다.
- **부수 효과**: "왜 병렬을 했는가"뿐 아니라 **"왜 X1·X2에는 병렬을 안 했는가"**도 데이터로 설명된다.
- **주의**: 라우터 규칙을 questions.json 30개에 과적합시키지 않는다. 30개는 검증용이지 학습용이 아니다.

### D4. NL2SQL — 도구 내부에서 LLM이 SQL 생성

`nl2sql` 도구가 Ollama를 호출해 스키마 + 질문 프롬프트로 SQL을 생성하고, 실행 후 결과를 반환한다. SELECT만 허용.

- **이유**: 라우터는 도구에 자연어 질문을 넘기므로(A안·B안 공통) SQL 변환은 `nl2sql` 도구 내부에서 일어나야 함. 규칙/템플릿 변환은 데이터셋 과적합이라 배제(팀 방침).

### D5. 지식 그래프 — PostgreSQL 테이블 + 재귀 CTE

nodes.json/edges.json을 PostgreSQL 테이블(nodes, edges)로 적재하고, 다단계 관계 탐색은 recursive CTE로 구현.

- **이유**: 과제 흐름도상 모든 도구가 PostgreSQL로 향함. "PostgreSQL 기반 지능형 데이터 플랫폼" 취지 부합, 추가 인프라 없음. Apache AGE는 RAM 4GB 제약에 부담, 인메모리 JSON은 플랫폼 그림에서 벗어남.
- "온톨로지 기반" 요구는 그래프 스키마 문서(노드 5유형, 관계 7종)를 온톨로지 정의로 명시하는 것으로 대응.

### D6. 무매칭 질문은 정직한 거절

라우터에 후보 도구가 없는 질문(스몰토크, 데이터 범위 밖)은 도구를 호출하지 않고 구조화 거절 응답(`out_of_scope`)을 반환한다. 에이전트는 이를 받아 모른다고 답변한다.

- **이유**: 무관한 컨텍스트를 소형 LLM에 주면 환각 유발. **애매**(후보 있음, 상보 중복 구간 → D3 병렬)와 **무매칭**(후보 없음 → 거절)은 다른 케이스.
- **기각한 대안**: 무매칭 시 전 도구 병렬 폴백 (스몰토크에 DB 3회 조회 + 환각 위험), 최근접 도구 강제 라우팅.

### D7. 엣지케이스는 구조 레벨만 분석, 검증은 이원화

엣지케이스 분석은 **구조 레벨**(데이터셋 내용과 무관한 시스템 실패 유형)만 허용하고, 인스턴스 레벨(개별 질문·문서에 맞춘 튜닝)은 금지한다. 검증 세트는 둘로 나눈다: 자체 작성 엣지 세트(케이스 유형별) + questions.json(회귀 전용, 규칙 튜닝 사용 금지).

**경계선** — "분석"과 "튜닝"을 구분한다:

| | 허용/금지 |
|---|---|
| **자산 간 구조를 대조**한다 — 무엇이 어디에 중복되는가, 그래프가 테이블에서 도출되는가 | ✅ **허용.** 데이터셋 인스턴스가 아니라 스키마·자산 관계를 보는 일이다 |
| 개별 질문에서 **키워드·규칙을 역산**한다 | ❌ 금지 |
| 특정 질문을 맞추려고 **예외 규칙**을 넣는다 | ❌ 금지 (#5 처리 참조) |

열린 항목을 닫기 전에는 **문헌보다 먼저 데이터셋을 대조한다** ([reading-priority.md](./reading-priority.md) 티어 3).

**회귀는 2축으로 잰다** — questions.json의 결함 2건은 성격이 다르다.

| 축 | 기대값 | 근거 |
|---|---|---|
| **라우팅 축** — 고른 도구가 기대 도구와 같은가 | **29/30** | #5는 #25·#29와 구조가 같은데 배정이 반대다. 원칙적 규칙으로 셋 동시 만족 불가 → **알려진 불일치로 문서화**하고 예외 규칙을 넣지 않는다 |
| **실행 축** — 선택된 도구가 올바른 응답 *유형*을 내는가 | **30/30** | #23("서울물산")은 존재하지 않는 개체명이다. **정답을 "결과 반환"이 아니라 "개체 부재(T5) 응답"으로 재정의**한다 → 실패 케이스가 아니라 T5 검증 실물이 된다 |

- **이유**: 엣지 견고성과 과적합 방지 동시 충족. 30개가 전부 정상 매칭 질문은 아니지만(#23이 반례), 엣지 케이스는 거의 없으므로 자체 세트가 여전히 필요하다.
- **#5를 맞추지 않는 이유**: 30/30을 만들려면 "프로젝트 수는 nl2sql, 고객 수는 knowledge_graph"라는 근거 없는 예외가 규칙에 들어간다. 이건 이 조항이 금지하는 인스턴스 과적합이고, 자체 엣지 세트에서 같은 유형이 나오면 무너진다.
- 케이스 카탈로그: [edge-cases.md](./edge-cases.md) (자산 중복 / 라우터 경계 / 도구 실패 / 응답 품질 4개 카테고리).

### D8. 구현 스택 — 공식 MCP SDK 직접 사용 (air 미채택)

TypeScript + `@modelcontextprotocol/sdk` 1.30.0. 주최사 권장 프레임워크인 air(`@airmcp-dev/core` 0.3.0)는 채택하지 않는다. 프로토콜 리비전은 SDK가 지원하는 최신인 **`2025-11-25`**.

- **이유**: air 채택을 정당화하던 유일한 실질 기능은 **7-Layer Meter**(필수 참조 [2] Pylon-7의 계층을 계측)였는데, **실측에서 동작하지 않음을 확인했다.** `defineTool`에 `layer`를 명시해도 `meter-middleware.js`의 `classify()`가 도구 이름·파라미터만 보고 `layer` 속성을 무시한다(타입과 공식 문서에는 있는데 구현에 없다). 자동 분류 규칙도 완전 일치 정규식이라 우리 도구명이 하나도 걸리지 않아 모든 호출이 L4로 뭉개진다. 검증 상세는 [air-evaluation.md](./air-evaluation.md) 8절
- 도구가 4개뿐이라 보일러플레이트 절감은 결정 근거가 되지 못하고, 플러그인 19종 중 우리에게 맞는 것은 timeout·dedup 둘뿐이다(`retryPlugin`은 T1 제약과 충돌).
- 과제 문서가 air를 **"사용 의무는 없습니다"**로 명시하므로 미채택에 규정 위반은 없다. air를 검토하고 근거를 들어 기각한 기록 자체가 심사 서술이 된다.
- **기각으로 잃는 것과 대안**: Pylon-7 계층 계측은 포기하지 않는다. 도구 핸들러를 감싸는 얇은 래퍼에서 계층을 상수로 붙여 기록하며, air의 이름 패턴 추측보다 논문 계층 정의에 맞춰 우리가 명시하는 편이 정확하다 — `ask` = L5 Routing, 도구 3종 = L3 Resource.
- **부수 확인**: SDK 1.30.0의 `LATEST_PROTOCOL_VERSION`이 `2025-11-25`라, 스펙 문서상 최신인 2026-07-28 리비전은 **어떤 스택을 골라도 구현할 수 없다**. air의 리스크가 아니라 생태계 상태였다 ([mcp-spec.md](./references/mcp-spec.md) 참조).

### D9. 도구 경계는 "요구 출력 형태"로 가른다 (데이터 자산이 아니라)

라우터는 **질문이 어느 자산에 있는가**가 아니라 **어떤 형태의 답을 요구하는가**로 판별한다.

| # | 규칙 | 도구 |
|---|---|---|
| 1 | **서술**을 요구 — 원인, 방법, 절차, 내용, 결정, 제안 | `vector_search` |
| 2 | **정형 속성·수치 값**을 요구 — 금액, 연봉, 기간, 상태, 행 개수 | `nl2sql` |
| 3 | **개체 식별·연결**을 요구 — 누가/무엇을/어디 소속/담당 | `knowledge_graph` |
| 4 | **관계를 세는 집계** — 세는 대상이 관계이므로 규칙 3에 귀속 | `knowledge_graph` |

- **이유**: 자산 기준("각 도구는 하나의 데이터 자산에 대응")은 이 데이터셋에서 성립하지 않는다 — 그래프는 테이블에서 100% 도출되고, 문서 40건은 전부 그래프 개체를 언급하며, 티켓 title 28종 중 18종이 문서와 주제가 겹친다 ([dataset-analysis.md](./dataset-analysis.md)). 자산으로 가르면 겹치는 구간에서 규칙이 정의되지 않는다.
- **검증**: 이 규칙을 questions.json 30개에 **대조**한 결과 **29/30 일치** (vector_search 10/10, nl2sql 9/10, knowledge_graph 10/10). 유일한 불일치 #5는 데이터셋 내부 비일관성이다 (D7 회귀 2축).
  - 규칙 4를 뒤집으면 #25·#29 두 건이 대신 틀린다(28/30). **29/30이 원칙적 규칙의 상한**이다.
- **동일 중복(X1·X2) 처리**: 규칙 3·4가 우선순위 역할을 한다 — 관계만 물으면 `knowledge_graph`, 정형 속성이 함께 걸리면 `nl2sql`.
- **도구 설명(description)도 이 축으로 쓴다.** 자산으로 설명하면 설명끼리 겹쳐 hard negative가 된다 (Hasan et al. 2026 — compact하고 목적이 분명한 설명).

#### D9-a. 표층 신호는 **스키마 어휘**에서 뽑는다

위 규칙 4개는 **의미**로 쓰여 있다. 코드가 무엇을 보고 판정하는지는 별개 문제이고, **여기서 확정한다 — 스키마의 관계명·컬럼명에서 뽑는다.**

- **관계 어휘**: `USES` · `BELONGS_TO` · `HAS_PROJECT` · `LEADS` · `MANAGES_ACCOUNT` · `REPORTED_ISSUE` · `HEAD_IS` (7종)
- **속성 어휘**: `amount` · `salary` · `status` · `region` · `quarter` · `category` · `priority` · `budget` 등 테이블 컬럼

**왜 이 길인가.** D11이 밝힌 대로 판별 축은 출력 형태가 아니라 **피연산자(관계 vs 속성)**이고, 스키마 어휘가 정확히 그 축의 표층형이다. 그리고 **D7이 허용하는 유일한 길**이다 — 스키마는 질문보다 먼저 있던 구조이므로 인스턴스 역산이 아니다.

**기각한 대안 2건 (실측 근거 있음)**:

| 대안 | 결과 |
|---|---|
| **의문사 매핑** (`어떻게/왜`→서술, `얼마/몇`→수치, `누구/어디`→개체) | **실패.** 개체 태그 8건이 `nl2sql` 2 / `knowledge_graph` 6으로 갈리고, **9건이 무태그**이며 `#28`이 오분류된다 ([dataset-analysis.md](./dataset-analysis.md) 5장). 의문사는 **출력 형태** 축의 신호라 두 도구를 못 가른다 |
| **questions.json에서 키워드 목록 역산** | **D7 금지.** 30개는 회귀 전용이며 결함 2건을 포함한다. 역산하면 검증 수단이 사라진다 |

**거친 1차 구현으로 28/30**이 나온다 ([dataset-analysis.md](./dataset-analysis.md) 5장 재현). 미스 2건은 성격이 다르다 — `#5`는 알려진 데이터셋 불일치, `#17`("고객사 미팅에서 논의된 일정 지연 **이슈**는?")은 `REPORTED_ISSUE`의 "이슈"가 일반 명사와 충돌한 **표층 문자열 충돌**이다 (edge-cases.md **R5**).

> **주의 — 이 28/30을 실력으로 치지 않는다.** 한국어 표층형 매핑(`담당`→`MANAGES_ACCOUNT` 등)을 사람이 썼고, 그 사람이 30개를 이미 읽은 뒤였다. **출처가 스키마인지 질문인지 방향이 흐려졌을 위험이 있다.** 자체 엣지 세트로 다시 재기 전까지는 "방향이 맞다"까지만 주장한다.

### D10. 부분 응답 — 요구 형태 미충족을 구조화해 반환

질문이 요구한 출력 형태를 담은 자산에 자료가 없고 **다른 자산에 인접 사실만 있을 때**, 응답은 **"요구 유형의 자료 없음"과 "확인된 인접 사실"을 별도 필드로 분리**해 반환한다.

```jsonc
{
  "status": "partial",
  "requested_form": "narrative",
  "unavailable": { "asset": "documents", "reason": "no_document_for_entity" },
  "adjacent_facts": { "source": "knowledge_graph", "data": [ /* ... */ ] }
}
```

`unavailable.asset`과 `adjacent_facts.source`는 **도구 3종 전부를 값으로 갖는다** — `documents` / `graph` / `tables`. 위는 한 조합의 예시일 뿐이다. (필드 구조 자체는 열어둔 항목 "거절·부재 응답 스키마"에 종속된다.)

- **왜 필요한가 — 세 도구 전부에서 상시 발생한다**: 커버리지를 **(개체 × 요구 형태) 격자**로 재면 문서 **10/60**, 그래프 **322/416**, 테이블 **106/120** 칸만 차 있다 ([dataset-analysis.md](./dataset-analysis.md) 3장). 예외가 아니라 정상 경로다.

  | 도구 | 빈손이 되는 질문 | 인접 사실 |
  |---|---|---|
  | `vector_search` | "Client-P의 장애 원인은?" / "Product-C1의 API는?" | 그래프·테이블에 개체 사실 |
  | `knowledge_graph` | "이 직원이 이끄는 프로젝트는?" (직원 43/45가 관계 일부 결손) | 소속 부서, 담당 고객 |
  | `nl2sql` | "Client-X의 진행 중인 프로젝트는?" (8개 고객사 0행) | 계약·매출·티켓 |

  **빈손 3종(edge-cases T3·T4·T7)이 전부 X5 승격 후보다.** 승격하지 않으면 확인된 사실을 버린다. T5(개체 자체가 없음)만 승격 대상이 아니다.
- **그냥 인접 사실만 넘기면 안 되는 이유**: 원인을 물었는데 "이슈가 있었다"는 사실만 주면 소형 LLM이 그로부터 원인을 지어낸다 — Q1(환각)이 발생하는 정확한 지점이다. 응답만 보고는 모델이 "원인"인지 "인접 사실"인지 구분할 수 없다.
- **거절(D6)과 다르다**: 거절은 후보 도구가 없는 것, 부분 응답은 **도구도 맞고 개체도 있는데 요구 형태만 없는 것**이다. MCP 스펙상 둘 다 `isError` 없는 정상 결과이고 `structuredContent`로 구분한다.
- **에이전트 규약**: 부분 응답을 받으면 인접 사실을 요구된 답인 것처럼 말하지 않는다. *"원인 기록은 없습니다. 다만 …한 기록은 있습니다."*
- **기각한 대안**: 요구 형태 미충족 시 전면 거절 (격자 빈칸이 세 자산 전부에 있어 시스템이 **상시** "모른다"고 답함 — 문서는 칸의 83%가 비어 있다), 있는 것만 그대로 반환 (Q1 환각 위험 그대로).

### D11. 도구 능력 시그니처 — 설계 어휘 (런타임 파서 아님)

도구를 **(연산 × 피연산자 × 출력 형태)** 시그니처로 적는다. 이는 **설계·문서 어휘**이고, 질문을 파싱하는 런타임 계획기를 만들지 않는다. 문헌 대조는 [references/question-taxonomy.md](./references/question-taxonomy.md).

#### 1. 도구 3종 시그니처

| 도구 | 연산 | 피연산자 | 출력 형태 |
|---|---|---|---|
| `vector_search` | 없음 (유사도 검색) | 문서 청크 | **서술** — 원인·방법·절차·결정·제안 |
| `nl2sql` | 집계(SUM·COUNT·AVG) · 필터 · 정렬/최상급 · 조인 | **정형 속성** | 수치 · 속성값 · 행 목록 · **개체**(집계+최상급일 때) |
| `knowledge_graph` | 순회(1~N홉) · 집계(COUNT) | **관계** | 개체 · 개체 목록 |

#### 2. D9의 판별력은 출력 형태가 아니라 **피연산자** 축에서 나온다

`nl2sql`도 개체를 출력하고(`#9` "평균 연봉이 가장 높은 부서는?"의 답은 부서다) `knowledge_graph`도 개체를 출력한다. **출력 형태만으로는 두 도구가 갈리지 않는다.** 가르는 것은 피연산자가 속성이냐 관계냐다.

- **D9 규칙 4가 이미 그렇게 쓰여 있다** — *"세는 대상이 관계이므로 규칙 3에 귀속"*. 출력 형태가 아니라 피연산자로 가른 서술이다.
- `#9`를 현행 규칙 2(정형 속성·수치)가 맞추지만, **맞추는 이유는 "요구된 답의 형태"가 아니라 "피연산자가 속성"이기 때문이다.** 규칙 이름과 실제 판별 근거가 어긋난다.
- **문헌 대조**: 답 유형 단일 축의 원형인 Li & Roth (COLING 2002)가 경계 불명확을 이유로 다중 라벨을 허용했고, 집계·비교/최상급을 답 유형의 하위 클래스로 둔 체계는 조사 범위에서 하나도 없었다 (question-taxonomy.md 7장).
- **D9 규칙 4개는 바꾸지 않는다.** 29/30이 원칙적 규칙의 상한이고 2축으로 재작성해도 판정이 같다. 이 항은 **규칙이 실제로 무엇을 재는지를 기록**하는 것이다.

#### 3. 요구 집합 어휘 — `requested_form` 값의 출처

질문의 요구를 **`{(연산, 피연산자, 출력 형태)}` 집합**으로 적는다. D10 스키마의 `requested_form`이 이 어휘를 값으로 갖는다.

| 값 | 뜻 | 담는 자산 |
|---|---|---|
| `narrative` | 서술 — 원인·방법·절차·결정·제안 | 문서 |
| `attribute` | 정형 속성값 — 금액·연봉·기간·상태 | 테이블 |
| `aggregate` | 집계 결과 — 합·개수·평균 | 테이블 또는 그래프 |
| `entity` | 개체 식별 — 누가·무엇이 | 그래프 또는 테이블(집계+최상급) |
| `entity_list` | 개체 목록 · 관계 순회 결과 | 그래프 |

#### 4. 단일 / 병렬 / 부분은 요구 집합의 성질에서 유도된다

| 요구 집합 | 방법 | 현행 대응 |
|---|---|---|
| 원소 1개, 자산에 있음 | **단일 호출** | 기본 |
| 원소 2개+, 서로 다른 도구가 커버 | **병렬 → 병합** | X3 · X4 |
| 원소 2개+, 같은 도구가 커버 | **단일 선택** | X1 · X2 |
| 원소 중 일부가 격자 빈칸 | **부분 응답** | X5 |
| 원소 0개 (후보 도구 없음) | **거절** | R1 |
| **원소 간 의존** (B의 인자 = A의 출력) | **아래 5** | **R4 (신설)** |

**구현은 X1~X5 카탈로그 그대로 둔다.** 이 항은 카탈로그가 왜 그렇게 갈리는지의 근거이지 대체물이 아니다.

#### 5. 의존 탐지 — 이 항의 유일한 런타임 요건

요구 집합의 한 원소가 **다른 원소의 출력을 인자로 요구**하면(멀티홉), 라우터는 도구를 실행하지 않고 **정의된 상태**를 반환한다.

- **왜 필요한가**: 멀티홉 실행은 기각했다 — 출처 문면 0건, questions.json 30/30이 단일 홉, 그리고 중간 결과를 읽고 다음 호출을 정하는 일은 규칙으로 불가능하고 LLM에 맡기면 **D1 방어선이 무너진다**(Shen et al., *Small LLMs Are Weak Tool Learners*, EMNLP 2024). **그러나 기각은 "안 만든다"이지 "안 들어온다"가 아니다.** 지금은 `"Client-A가 쓰는 제품의 장애 원인은?"` 같은 질문이 규칙 1에 걸려 **개체 한정어가 무시된 채 아무 장애 문서나 반환된다** — 조용히 틀리는 형태이고, X5도 R1도 아니다.
- **탐지 조건 (규칙)**: 질문에 개체 한정어가 있고 · 그 개체가 요구된 출력 형태를 담은 자산에 **직접 없으며** · 다른 자산의 관계 순회로만 도달 가능할 때.
- **파서가 아니다.** 판별 함수의 한 갈래이며 A/B 배치와 무관하다.
- **반환 형태는 미정** — 부분 응답(D10)이냐 거절(D6)이냐. 열어둔 항목.

**기각한 대안**: 질문 파서·실행 계획기·체이닝 실행기 도입 (과제의 "규칙 기반" 문면과 어긋나고, 라우팅 정확도는 29/30 상한 그대로이며, 실행하지 않을 능력을 만드는 것이다), D9 규칙 4개를 2축으로 재작성 (같은 판정을 다르게 적는 것).

### D12. 라우터 도구 선택은 시그니처 임베딩으로 한다 (표층 어휘 매칭이 아니라)

라우터는 **도구 3종의 능력 서술 1문장씩**과 질문을 임베딩해 가장 가까운 도구를 고른다.
거절(R1)은 별도 임계로 가른다. 판별 함수는 이렇다.

```
route(question):
  hit ← 질문에 [테이블 표층형 8개 ∪ 저카디널리티 컬럼 값] 이 걸리는가
  if not hit:
      if maxdoc(question) ≥ 0.52  →  vector_search      # 표층 충돌(R5) 해소
      elif 개체 한정어 없음        →  out_of_scope       # 거절(R1)
  →  도구 시그니처 임베딩 argmax                           # 도구 선택
```

`maxdoc`은 질문과 문서 청크의 최대 코사인 유사도다. 파라미터는 임계 하나뿐이다.

- **왜 바꾸는가 — D9-a의 방침이 반증됐다.** 이슈 #7이 *"두 점수가 모두 낮으면 D9-a(표층 신호 = 스키마 어휘)
  자체가 반증된 것"*이라고 미리 적어 두었고, 그 조건이 충족됐다. 스키마에서만 기계 생성한 표층 사전은
  회귀 14~18/30 · 자체 엣지 세트 8~13/29였다. **`dataset-analysis.md` 5장의 28/30은 사전의 성과이고,
  그 사전은 30문항을 읽은 뒤 사람이 쓴 것이다** — 같은 형태를 스키마만으로 만들면 14/30으로 떨어진다.
- **실측**: 시그니처 임베딩 argmax 단독으로 회귀 24/30 · 엣지 16/29. 위 게이트를 얹으면 **회귀 26/30 · 엣지 21/29**다 (라우팅 축). **엣지 실행 축 16/29 는 인용하지 않는다 — 점수가 아니라 포화 상한이다**: `route()` 가 `parallel_merge`·`partial`·`entity_not_found` 를 낼 경로가 없어 도달 최대치가 16이고 실측이 그 값이다 ([harness-evaluation.md](./harness-evaluation.md) 4절 †)
  (현행 28/30 · 13/29). 임계는 **0.48~0.57 열 칸에서 점수가 같다** — 칼날 튜닝이 아니다.
- **하이브리드는 값어치가 없다.** 표층 규칙을 1차로 두고 임베딩을 폴백으로 쓰면 회귀 +2, **엣지는 0**이다.
  그 +2도 오염된 수작업 사전에서만 나오고, 기계 사전으로 하면 -5다.
- **게이트 사전은 거칠어도 된다.** 관계 7종·컬럼 24종의 표층형 목록은 **불필요해졌다** —
  테이블명 8개 + 컬럼 값이면 같은 점수가 나온다. 게이트는 "걸렸는가"만 보기 때문이다.
- **"규칙 기반" 문면과의 관계**: 요강이 대비시키는 것은 **LLM이 도구를 고르는 방식**이고,
  임베딩 유사도는 LLM 판단이 아니라 결정적 함수다. D1의 방어선(소형 LLM에게 도구 선택을 맡기지 않는다)은
  그대로 산다. 다만 현행보다 문면에서 먼 것은 사실이므로 심사 설명에 이 정의를 명시한다.
- **임베딩 모델은 `bge-m3`로 확정한다.** `nomic-embed-text`는 라우팅이 13/30이고
  **거절 임계가 성립하지 않는다**(R1 최대 0.804 > `vector_search` 최소 0.712 — 구간이 겹친다).
  `document_chunks.embedding`을 **`vector(1024)`**로 바꿔야 한다.
- **기각한 대안**: 표층 사전을 사람이 쓰기(28/30을 얻지만 역산 오염을 절차로만 방어해야 하고 엣지는 13~18/29),
  하이브리드(위), LLM에게 도구 선택 위임(D1 위반).

**병렬 승격을 넣었다 (2026-08-21).** 판정이 2단계다 — ① 접속 탐지로 요구 원소가 둘인지 보고 ② 후보 둘을 **실제로 태워 둘 다 `ok`일 때만** 병렬로 굳힌다. 접속만으로는 부족하다: *"장애 사례와 원인"* 은 접속돼 있지만 두 요구가 같은 도구에 걸린다(D11-4의 동일 중복). **회귀 26 → 24로 2점을 내주고 엣지 라우팅 22 → 25, 실행 22 → 27을 샀다.** 내준 2점(`#4`·`#10`)은 두 도구가 다 답할 수 있는 동일 중복 구간이라 실행 결과만으로는 안 갈린다.

**포화는 도구로 풀었다 (2026-08-21).** 낼 수 없던 13칸 중 7칸(`partial` 5 · `entity_not_found` 2)은 라우터가 아니라 **도구 실행 결과**를 요구했다. `vector_search`·`knowledge_graph` 를 실제로 구현하자 **라우팅 축을 한 점도 내주지 않고** 엣지 실행 축이 16/29(상한 16) → **22/29**(상한 23)가 됐다. 라우팅은 오히려 21 → 22로 올랐다 — 상호 접미사 목록이 도구에만 있어 라우터가 `T5-01`을 먼저 거절하던 것을 `assets/entity-patterns.json` 으로 공유해 고쳤다. **관계 어휘는 `knowledge_graph` 안에 둔다** — D12가 불필요하다고 정한 것은 *도구 선택*에서이지 관계 *순회*에서가 아니다. 근거와 수치는 [harness-evaluation.md](./harness-evaluation.md) 4절.

### D13. 하네스 자산을 저장소에 둔다

프롬프트·컨텍스트·호출 옵션을 코드에 흩지 않고 [`harness/assets/`](../harness/README.md)에 모은다.
자산은 두 종류이고 **섞어 부르지 않는다** — `build_assets.py` 가 둘 다 내보내지만 출처가 다르다.

| 종류 | 무엇 | 출처 |
|---|---|---|
| **파생** | `schema-annotated.sql` · `column-values.json` | 데이터셋에서 기계 추출. 사람 손이 닿지 않는다 |
| **저작** | `tool-signatures.json` · `model.json` · `surface-gate.json` 의 `tables` · 프롬프트 2건 | **사람이 썼다.** 각 파일의 `_provenance` 필드에 명시한다 |

**저작 자산에는 D12 가 옛 표층 사전을 기각할 때 든 것과 같은 오염이 남아 있다** — 작성자가 30문항을 읽은 뒤였다. 한계는 [harness-evaluation.md](./harness-evaluation.md) 6절에 기록한다.

- **왜 필요한가 — 모델을 안 바꾸고 성능이 크게 움직인다.** `nl2sql` 실행 정확도가 홀드아웃 48문항에서
  **50% → 90%**로 올랐다. 바꾼 것은 전부 모델 바깥이다 ([harness-evaluation.md](./harness-evaluation.md)).
- **핵심 규약 셋**:
  1. **값·단위는 DDL 컬럼 옆 인라인 주석으로 둔다.** 같은 정보를 별도 블록에 두면 75%, 인라인이면 90%다.
     단위 문항만 보면 2/7 → 7/7이다. TACC가 말한 선별 구성이 우리 데이터에서는 **배치**로 나타났다.
  2. **규칙을 더 넣지 않는다.** 개발 실패를 보고 규칙 넷을 더하면 개발 90% · 홀드아웃 81%로 갈린다 (탐색 측정).
     [related-work.md](./references/related-work.md) 5.4 Hasan et al.의 과보강 퇴행과 같은 형태다.
  3. **`think: false`를 고정한다.** 켜면 숨은 추론 토큰이 `num_predict`를 소진해 **빈 응답**이 나온다
     ([edge-cases.md](./edge-cases.md) T1).
- **테스트 세트를 개발 48 / 홀드아웃 48로 나눈다.** 튜닝은 개발만 보고 하고 홀드아웃은 하네스당 한 번만 잰다.
  **두 점수의 격차를 기록한다** — 격차가 과적합 지표다.
- **`questions.json` 30개는 이 측정에 쓰지 않는다.** 30개에 맞추는 것은 목적이 아니다 (D7).

### D14. 실행 실패는 도구 안에서 잡는다

DB 연결 실패 같은 인프라 오류(T6)를 **도구 3종 전부**가 `{status:"error", reason}` 으로
돌려준다. `nl2sql` 만 그것을 내던 상태에서는 나머지 둘이 예외를 그대로 던져
`ask` 응답이 통째로 사라졌다 — 실패 시점에 정확히 `routed_to`·`matched_rule` 이 없었다 (#17).

- **`compose` 한 곳에서 잡지 않는다.** 도구 3종은 개별 검증·시연·심사 창구로 등록돼 있고
  (D2), 그 직접 호출은 `compose` 를 지나지 않는다. 한 곳에서 잡으면 `ask` 만 구조화되고
  창구 셋은 여전히 봉투 없이 죽는다.
- **라우팅·임베딩 단계의 실패는 봉투 없이 죽는 것을 허용한다.** 도구를 고르기 전에 죽으면
  채울 `routed_to` 자체가 없다. 그 잔여 모양은 에이전트의 `isError` 가드가 덮는다 (D15).
- **재시도를 여기에 넣지 않는다** (#17 확정 제약). 임베딩 전송 재시도(`src/ollama.ts`)는
  전송 실패에 대한 것이고, 이것은 그 위 계층이다.
- 데이터 부재(T3~T5·T7)는 지금 동작 그대로다 — 에러가 아니다 ([edge-cases.md](./edge-cases.md) 공통 규약).
- `harness/build/tools.py` 도 같은 래퍼를 갖는다. 한쪽만 고치면 대조 59/59 가 그 순간 갈린다.

### D15. 에이전트 — `ask` 하나만 부르고 응답 상태대로 답한다

과제 컴포넌트 ④. [`src/agent/`](../src/agent/) 다섯 모듈이고 얇다 — 판별·실행·병합은
서버가 한다 (D1). 결정 아홉 개를 여기 모은다.

**① `ask` 를 코드가 하드코딩한다 (Q4).** stdio MCP 클라이언트가 `listTools` 를 부르지 않고
도구 이름 상수 하나만 갖는다. LLM 에 도구 목록도 선택권도 주지 않는다 — 프로토콜은 도구 4개를
전부 노출하므로 우회를 막는 것은 코드뿐이고, 시스템 프롬프트 지시로 두면 소형 모델에서 샌다.
이것이 D2 *"부수 효과"* (에이전트 입장에서 선택지가 1개)의 성립 조건이다. 검증은 호출 로그로
한다 — 나간 호출이 전부 `logs/agent-calls.jsonl` 에 남는다.

**② `isError` 가드 — 실패에는 LLM 을 태우지 않는다.** `isError` 이거나 `structuredContent` 가
없으면 고정 문자열을 답으로 낸다. 읽을 구조화 응답이 없는 상태에서 생성을 돌리는 것이 정확히
환각이다 (Q1). **두 실패 모양을 가드 하나가 덮는다** — 도구 실행 실패(D14)와, 라우팅·임베딩
단계에서 죽어 봉투가 통째로 사라진 모양. 뒤쪽은 D14 가 도구 래퍼로 덮지 않기로 한 잔여다.

**③ 봉투를 도구 결과 모양으로 편다.** `ask` 봉투를 통째로 프롬프트에 넣으면 모델이 `routed_to`·
`why` 같은 라우팅 메타데이터까지 답의 재료로 읽는다. `results[routed_to[0]]` 항목 하나로 펴면
`harness/tests/answer-protocol-dev.json` 이 채점하는 모양과 같아진다. **실측 20/28 대 19/28,
토큰 −116.** 가르는 기준은 개수가 아니라 봉투 `status` 다 — 병렬 되돌리기 경로(`composition.ts`)가
`results` 2개인 채로 `single` 류를 낼 수 있어 개수로 가르면 오판한다.

**④ 선별은 `ask` 안에 둔다 (TACC 적용 실물).** 무관 필드 정규식 + 동명이인 힌트 축약
([`src/curation.ts`](../src/curation.ts)). **실측 — `OP-05` 가 `아니오` → `예` 로 돌아섰고
ambiguous 판정이 2/8 → 8/8** 이 됐다. 힌트가 관계 전량이면 모델이 되묻지 않고 그 안의 이름
하나를 답으로 고른다. **도구 3종 직접 호출 경로에는 걸지 않는다** — 심사·시연 창구는 원본을
보여야 하고, `harness/build/tools.py` 와 갈라지면 대조 59/59 가 깨진다.

**유사도 숫자를 선별에서 지우는 안은 하지 않았다.** 모델이 `sim` 값을 답에 그대로 옮겨
적는 것이 관측돼 있었는데(vector 관여 23문항 중 3건, 한 건은 `0.7183327628673172` 전량),
D16 이 문서 본문을 실은 뒤 **3회 실행 모두 0/23** 이 됐다. 겨냥할 실패가 남아 있지 않아
구조를 늘리지 않는다.

**⑤ 절사 5000자는 에이전트에 두고, 안전장치다.** 런타임 컨텍스트는 `num_ctx = 4096`(Ollama
기본값이고 모델 상한 131072 과 무관하다)이고 `num_predict` 가 400이므로 **프롬프트 예산은
3696토큰**이다. 실측하면 그것이 context 약 5350자에서 찬다 (본문 4422자 = 3151토큰 ·
5524자 = 3797토큰). **종전 값 6000자는 그보다 커서 안전장치가 아니었다** — 그 구간에서는
`fitBudget` 이 덜기 전에 Ollama 가 먼저 조용히 자르고 `truncations` 는 빈 채로 남는다.
드러나지 않은 것은 실측 최대가 1269자였기 때문이고, 종전 서술이 인용한 *선별 전* 관측 최대
4949자는 5350자 상한 **바로 아래**였다. 문서 본문을 싣는 #25 가 실측 최대를 **3245자**로
올렸고, 5000자는 그 위에 여유를 남기면서 토큰 상한 아래다. 선별 후 59문항 **절사 0건** —
평소에는 여전히 걸리지 않는다. **행 상한은 두지 않는다**: 상한을 두면
안 넘치는 질문에서도 행이 잘린다(회귀 `#22` 10→3명, `#28` 8→3건에서 판정 불변을 확인했다).
넘치면 가장 긴 배열의 마지막 행부터 덜고 **무엇을 얼마나 덜었는지 로그에 남긴다** (Q2) —
조용한 절사는 "다 넣었다"로 읽힌다.

**⑥ 프롬프트는 고치지 않는다 (D13 규약 2).** 확장안 셋을 실측했고 전부 내려갔다 —
B(상태별 지시 추가) 형식 8/8 → 7/8 · 판정 7/8 → 6/8, C 형식 7/8 · 실측 세트 5/8 → 3/8,
D 형식 7/8 · 판정 6/8. 노린 `X5-04` 는 세 안 모두 3/3 실패 유지였다. 규칙을 더하면 과적합한다는
같은 형태다.

**⑦ 동명이인 부록 줄은 코드가 붙인다.** 평탄화 결과가 `ambiguous_entity` 면 LLM 출력 뒤에
`후보: <name>(<type>: <hint>) / …` 한 줄을 덧붙인다. 프롬프트에 규칙을 더하지 않기 위한
자리이고(⑥), 채점기는 앞 3줄만 읽으므로 하네스 점수와 갈라지지 않는다.

**⑧ 채점은 3축이다** ([`scripts/agent-check.mjs`](../scripts/agent-check.mjs)).

| 축 | 대상 | 방향 |
|---|---|---|
| **호출** — 첫 호출이 `ask` 이고 직접 호출 0건인가 | 59문항 | 불변식 (깨지면 실패) |
| **환각** — 답 없는 상태인데 `답변가능: 예` 인가 | 59문항 | **단방향** |
| **응답** — `답변가능` 라벨이 기대와 같은가 | 엣지 29 중 상류 건전 문항 | 양방향 |

실측 수치는 [`harness-evaluation.md`](./harness-evaluation.md) 7절이 원본이다 — 여기 복제하지
않는다. #20 에서 채점 규칙이 바뀌자 이 표의 사본이 21/29 로 표류한 것이 실물이다 (#28).

**환각 축이 단방향인 이유**: `status: ok` 는 *"행이 왔다"* 이지 *"질문에 답한다"* 가 아니다.
요구한 관계가 아닌 행이 와도 `ok` 이므로, 그 경우의 `아니오` 를 오답으로 세면 도구가 옳게 낸
것을 채점기가 틀렸다고 하게 된다. 회귀 #17 이 그 실물이다. 반대 방향은 응답 축이 엣지 세트의
`expected.response` 라벨 위에서만 잰다 — **`questions.json` 30문항에 답변가능 라벨을 새로
붙이지 않는다** (D7, 이슈 #18 범위). 응답 축은 상류가 건전한 문항만 채점한다 — 오류 가드 ·
`no_result` · 라우팅 불일치는 기대 라벨 자체가 성립하지 않으므로 분모에서 빼고 `제외` 로
보고한다. 근거는 실패 6건 사람 판정이다 (#20, [`harness-evaluation.md`](./harness-evaluation.md) 7.5).

**⑨ 호출 로그를 남긴다.** `logs/agent-calls.jsonl`, 1질문 1레코드. `calls`(호출 축) ·
`truncations`(Q2) · `flat_status`(환각 축 입력) · `answer_first_line`(응답 축 입력) ·
`context_json`(절사 후 프롬프트 투입분 전문) · `answer_text`(LLM 출력 전문 — 뒤 둘은 응답 축
라벨 판정의 원천, #20)가 들어간다. 저장소에는 넣지 않는다(`.gitignore`) — 측정마다 다시 만들어진다.

### D16. 도구 반환은 판정 근거를 담는다 — 식별자·점수가 아니라

도구가 안 실은 것은 선별로 되살릴 수 없다. `ask` 의 선별(D15 ④)과 평탄화(D15 ③)는
**있는 것을 고르는** 계층이므로, 요구된 답이 반환에 없으면 그 아래에서 할 수 있는 일이 없다.

- **사례 1 — `vector_search` 가 문서 본문을 반환한다** (#25). 종전에는 `doc` 과 `sim` 뿐이라
  *"원인이 뭐야"* 류 질문에서 요구된 답이 컨텍스트에 **물리적으로 존재할 수 없었다.**
  그 결과 모델은 내용이 아니라 *"…문서에서 관련 내용이 검색되었습니다"* 를 답했고,
  응답 축은 라벨만 보므로 이것을 통과시켜 왔다. 실측은
  [harness-evaluation.md](./harness-evaluation.md) 7.6.
- **사례 2 후보 — `knowledge_graph` 행에 앵커 개체를 싣는다** (#26, **미착수·미검증**).
  같은 원리의 적용으로 보이며, 그렇다면 **한 문항을 맞추려는 예외가 아니다** (D7) — 앵커는
  모든 graph 결과에 일괄로 실리거나 안 실리거나다. 다만 **이 조항이 #26 을 미리 승인하지
  않는다**: #26 의 AC 는 `X2-01` 3회 반복 실측을 요구하고, 그 문항은 같은 프롬프트에서도
  라벨이 흔들리는 유일한 문항이다 (7.6). 원리가 사례를 하나 더 얻는지는 재 봐야 안다.

**기각한 대안 셋** — 전부 #25 에서 재 보고 뺐다.

| 대안 | 왜 뺐나 |
|---|---|
| 본문 앞 N자 절단 | `## 원인 분석` 이 문서 중간이라 요구된 답을 정확히 잘라낸다. 이 데이터셋은 문서 40건이 청크 40개(310~542자)여서 **청크가 곧 문서 전체**이고, "스니펫"이라는 선택지 자체가 없다 |
| 질문 관련 절만 추출 | 새 판정 규칙이 필요하고 그 규칙이 T4-form(#13)의 영역이다. 반환 형태 결정에 판정을 섞지 않는다 |
| `num_ctx` 상향 | `model.json` 은 하네스 자산이라 이전 실측치의 전제가 전부 무효가 된다 (D13, 7.4). 실측 최대가 예산 안에 들어 필요도 없었다 (7.6) |
| 행수를 5보다 줄이기 | `X3-01` 의 근거 문서 4건이 **2·3·4·5위**에 있고 1위는 무관하다 — 줄이면 이 이슈가 고치려는 유일한 엣지 문항을 못 고친다. 개체가 걸린 질문은 필터가 이미 2~3행으로 좁힌다. **행수를 늘려 보지는 않았다** |

**반환 값의 *표현* 도 판정을 바꾼다 — 두 건을 재 보고 기각했다.** 하네스와 서버를 맞추면서
서버 쪽 표현을 "더 옳아 보이는" 쪽으로 고쳐 봤더니 둘 다 응답 축을 깎았다.

| 바꿔 본 것 | 결과 (같은 프롬프트 5회) |
|---|---|
| `sim` 을 소수 3자리로 반올림 | `X5-02` 정답 5/5 → **오답 5/5** (`0.5197…`→`아니오`, `0.520`→`예`) |
| 집계 `count` 를 문자열에서 숫자로 | `X1-01` 정답 5/5 → **오답 5/5** |

종단에서도 18/21 → 16/21 → 14/21 로 중첩해 내려갔다. **소형 모델은 숫자 표현에 민감하고,
그 민감함이 판정을 바꾼다** — 두 구현을 맞출 때 어느 쪽으로 맞출지는 미관이 아니라 실측으로
정한다. 지금은 하네스를 서버에 맞춘다.

| LLM 모델 | **모델 확정 — `gemma4:e2b-it-qat`** (4GB 미달은 다음 행 — 대응 없음) | 블로그·공지가 **동일 문면**으로 `Gemma 4 E2B (Ollama 로컬 실행)`을 권장 개발 환경 표에 명시하고(2026-08-14 재확인), Ollama 레지스트리에 실물이 있다 ([dataset-analysis.md](./dataset-analysis.md) 7장). KOSSA 요강의 `소형 LLM(7B)` 표기와의 차이는 **사실로 존속**하나 **문의 후보 지위는 해제한다** — 과제 상세·데이터셋의 주체인 리원에이스 2출처가 일치하므로 문의로 얻을 정보가 없다. 태그는 `gemma4` 최소 태그인 **`e2b-it-qat`(4.3GB)**로 정한다 — 한국어로 답한다. **남아 있던 CPU 전용 실측은 2026-08-18에 끝냈고 결과가 부정적이다** — `num_gpu:0`을 강제하면 `ollama ps`가 **4.0GB · `100% CPU`**로 나온다. GPU 적재값(1.7GB)의 **약 2.4배**이고 제약 하한 4GB와 같다. **따라서 GPU 수치를 요구 메모리의 대리값으로 쓴 이전 판단(단독 1.7GB·3종 2.7GB)은 폐기한다.** `e2b`(7.2GB) 상향도 검토 대상에서 뺀다 — 최소 태그가 이미 하한에 닿았다. 대응은 다음 행 |
