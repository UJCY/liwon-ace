### 결정 3-1의 근거

맞을 때까지 다시 돌려 성공 테이크만 건지는 것은 `CONTEXT.md` 가 금지한 **인스턴스 과적합을
영상으로 옮긴 것**이다. 그리고 B-on-A 가 파는 것이 *"모를 때 모른다고 한다"* 인데, 성공
테이크만 붙인 영상은 그 주장 자체를 깬다.

사전 검증에서 3/3 재현된 문항이 촬영에서 갈렸다면 그것은 영상 문제가 아니라 **우리가 모르던
사실**이다. 교체하기 전에 원인을 본다.

### 결정 5의 근거 — 전환을 스크립트 시작 **앞**에 두는 이유

터미널 구간은 스크립트가 자동으로 흘러간다. 전환을 중간에 두면 사람이 창을 맞춰야 하고,
거기가 원테이크의 유일한 사람 개입 지점이 된다. 앞에 두면 전환이 늦어도 아무것도 안 깨진다.

닫는 슬라이드는 만들지 않는다 — 전환이 2회가 되고, 두 번째가 정확히 위험한 자리다.

사람이 컨텍스트를 읽어야 갈리던 실패가 자동 분류로 넘어갔다. `xcheck` 의 57/57 → 52/52 는
총점이 준 것이 아니라 **축 구성이 바뀐 것**이다 — 짝 선택이 축 신호로 바뀌며 LLM 결합
문항이 2 에서 7 로 늘어 결정적 축에서 빠졌다.

**`29/30` 을 쓰지 않는다.** `CONTEXT.md` 의 그 값은 **기대값** 칸이고, 실측은
`harness-evaluation.md` 4.4의 **26/30** 이다. 오늘 다시 재도 26/30이며 엣지 22/29,
실행 16/29 포화까지 문서와 정확히 일치한다.

**`NL2SQL 50% → 90%` 는 역사적 실측이라 인용으로만 쓴다.** 오늘 재려면 96문항 × LLM
재실행이 필요해 값이 안 맞는다. 재현 절차는 `harness-evaluation.md` 1절에 있다.

카드에서 가장 센 줄은 **`속는다 0건`** 이다 — 실패 8건 중 사용자가 틀린 답을 믿게 된 건이
없다. `26/30` 은 방어적 숫자지만 이것은 공격적 숫자다.

## 이 세션에서 나온 발견

### 1. 시연 후보 하나가 오답을 내고 있었다 — `scripts/smoke.mjs`

*"서울 지역 고객사는 몇 곳이야?"* → 실행 간에 `4` 와 `1` 로 갈렸다. **DB 실측은 4.**
생성 SQL은 `SELECT COUNT(DISTINCT region) FROM clients WHERE region = '서울'` 로,
`COUNT(DISTINCT region)` 이라 당연히 1이 나온다.

- **이 질문은 `questions.json` 30개에 없다.** 연기 시험용으로 지어낸 질문이라 회귀로
  재 본 적이 없고, 그래서 오답인 걸 아무도 몰랐다.
- **`model.json` 의 `_note` 가 오늘 성립하지 않았다.** *"seed를 박으면 둘 다 1/5로
  고정된다"* 고 적혀 있지만 `seed:0 · temperature:0` 인 채로 갈렸다. 결정성은 프로세스
  안에서만 성립하고 실행을 가로질러서는 아니다.

**시연 질문에서 제외했다.** 이 두 건은 영상과 별개로 처리할 후속 항목이다.

### 2. 공식 질문이 병렬 호출을 발동시킨다

### 개정 (2026-08-27 오후) — Q3 을 교체했다

위 발견은 **이슈 #12 이전 상태의 기록이다.** `pair-select` 가 병렬 짝 선택을 유사도에서
축 신호로 바꾼 뒤, 공식 #10 은 실행마다 갈린다:

```
최근 서버 장애 사례와 원인을 알려줘
  single         / vector_search
  parallel_merge / nl2sql,vector_search      ← 짝이 knowledge_graph 가 아니다
  single         / vector_search
```

짝이 `knowledge_graph` → `nl2sql` 로 바뀌었고 절반은 병렬이 아예 안 뜬다. **어느 쪽이
나와도 구간 제목과 어긋난다.** `harness-evaluation.md` 4.3 이 같은 문항(`#10`)을 회귀
24~25/30 구간의 원인으로 이미 지목해 두었다.

그래서 3/3 재현되는 **엣지 X4-01** 로 갈았다 — `parallel_merge [knowledge_graph,
vector_search]` 로 구간 제목과 정확히 맞는다. **대가는 공식 질문이 4개에서 3개로 주는
것이고**, 얻는 것은 요강이 이름 붙인 "MCP Parallel 패턴"이 화면에서 계속 증명되는 것이다.
병렬 구간을 빼는 대안은 그래서 기각했다.

**부수 발견 — `--verify` 가 거짓 통과를 냈다.** 한 세션 안에서 3회를 돌리는데, 이 불안정은
세션을 가로질러야 보인다. 아침의 `서울 지역 고객사` 사고와 같은 형태다.

*"최근 서버 장애 사례와 원인을 알려줘"* → `status=parallel_merge`,
`routed=knowledge_graph,vector_search`. **요강이 이름 붙인 "MCP Parallel 패턴" 이
공식 예시 질문에서 저절로 뜬다.**

## Q6 직후 해석 화면 (10초)

당신이 말한 설계 의도의 착지점이다.

```
  ── 이 응답이 왜 이렇게 생겼나 ──────────────────────────────
    unavailable.asset     = documents          ← Client-P 문서가 없다
    unavailable.reason    = form_not_covered   ← 개체는 있다. '서술' 형태만 없다
    adjacent_facts.source = graph              ← 확인된 사실은 여기서 왔다

    "모른다" 가 아니라 "문서를 채우면 답해진다" 를 돌려준다.
    실패에 좌표가 붙으면, 다음에 무엇을 보강할지가 정해진다.
```

`unavailable` 은 거절이 아니라 **보수 지시**다 — 실패가 (자산 × 형태) 좌표를 가지므로
사용자가 안 속고(`속는다 0`), 고칠 데가 정해지므로 나아진다(확장성). 두 논거가 한 필드에서
나온다.
