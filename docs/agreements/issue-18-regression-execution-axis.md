> 2026-08-27 grilling 세션의 합의. 이슈 원문은 #18, 확정 제약은 D7.

## 판정 — 이슈의 반증 조건은 안 걸렸다

이슈는 *"라벨이 `q`를 읽지 않고도 정해지면 D7을 건드리지 않고 실행 축이 생긴다"*를
반증 조건으로 걸었다. 실측으로 닫는다: **그런 라벨은 없다.**

- 회귀 30을 `answer()`로 태운 실행 상태: `single` 26 · `parallel_merge` 2(#4·#10) ·
  `entity_not_found` 1(#23) · `partial` 1(#24).
- `q`를 안 읽고 만들 수 있는 라벨은 "전 문항 `single`" 하나뿐이다 — `tool` 필드가
  단수라는 사실만 쓴다. 이 라벨로 재면 26/30인데, 불일치 4건 중 #4·#10은 라우팅 축과
  중복이고 **#23·#24는 정직한 응답을 오답으로 센다.**
- **#23**: D7이 이미 "T5 응답이 정답"으로 재정의한 문항이다. 라벨을 `entity_not_found`로
  고치려면 문항을 읽어야 한다.
- **#24** *"Product-D1 제품과 관련된 프로젝트는?"*: 그래프에 product↔project 엣지가
  스키마상 없다 — 관계 7종 중 project에 닿는 것은 `HAS_PROJECT`(client→project)·
  `LEADS`(employee→project) 뿐이다 (dataset-analysis.md 관계 표). `partial`은 D10의
  정직한 응답이고 사실상 정답이다. 이것도 라벨로 만들려면 `q`를 읽어야 한다.
- 이슈가 든 유일 후보 T3("0행이 정상인가")은 실측에서 갈리는 문항이 없다 — 라우팅
  적중 24문항의 raw에 `no_result` 0건.
- 결정적 사각: `normalize`가 `error`→`single`로 접으므로(규약 — 실행 실패는 MCP
  `isError` 채널), 상태 레벨 실행 축은 **진짜 실행 실패를 원리적으로 못 본다.**
  실측에서 #0·#8이 raw `error`인데 상태는 `single`이다. 라벨을 붙여도 계측기가
  표적을 못 본다.

따라서 이슈의 우리 해석대로 **안 잰 것이 맞고, #7의 AC("59문항 2축")가 틀렸다** —
2축은 엣지 29에만 성립한다.

## 결정 1 — D18 신설: 회귀는 라우팅 축만 채점, 실행 상태는 라벨 없이 관측

- 회귀 30의 실행 상태에 **기대 라벨을 만들지 않는다** (사람 저작·스크립트 생성 모두).
  근거는 위 판정 세 줄 — 의미 있는 라벨은 D7 접촉이고, `q`-무접촉 라벨은 정직한 응답을
  오답으로 세며, 상태 레벨은 error를 못 본다.
- 대신 러너가 실행 상태를 **관측선**으로 낸다 — 채점 없는 기록. 실행마다 문항 단위로
  비교 가능한 분포가 라벨 없는 회귀 tripwire가 된다.
- D15 ⑧의 선참조 "(D7, 이슈 #18 범위)"는 D18 확정 인용으로 바뀐다 — 에이전트 응답
  축과 e2e 실행 축이 같은 결정 아래 선다.

## 결정 2 — 관측선 명세 (`run_e2e.py` `score_regression`)

출력 형태 (수치는 구현 시 재측정):

```
회귀 30문항  ·  라우팅 축 24/30  ·  실행 상태는 채점하지 않는다 — 기대 라벨 없음 (D18)
    실행 상태 관측: single 26 · parallel_merge 2(#4 #10) · entity_not_found 1(#23) · partial 1(#24)
    raw 접힘: #0(error→single) #8(error→single)
```

- 라벨·기대값·점수는 없다. 세 정보만 낸다: **상태 분포**, **비-`single` 문항 ID**,
  **raw가 `normalize`에 접힌 문항**(raw가 `ok`가 아닌데 상태가 `single`인 것 —
  `error`·`no_result`).
- 문항 ID와 raw 접힘 표시가 있어야 상쇄 변화(한 문항 `partial`→`single`, 다른 문항
  `single`→`partial`)가 보인다. 라우팅 미스 줄이 이미 문항 ID를 찍으므로 노출 종류는
  새롭지 않다.
- 관측선은 LLM 비결정을 그대로 드러낸다(#8이 실행마다 다를 수 있다) — 간헐 실패의
  가시화가 목적의 일부다.

## 결정 3 — #0·#8 조사 기록 (수정하지 않는다)

- **#0** *"서울 지역 매출 상위 5개 고객사"* — 안정 재현 (이 세션 3/3, 과거 에이전트
  로그도 "시스템 오류" 답변). 생성 SQL이
  `SELECT T1.name … ORDER BY SUM(T2.amount) DESC LIMIT 5` —
  **집계 상위 N 패턴에서 GROUP BY 누락.** 스키마 이해는 맞다 (`sales.region` 실존).
  T1로 구조화되므로 도구 규약(D14)은 지켜진다.
- **#8** *"2024년 등록 고객사 수"* — 간헐 (3회 중 1회 error: 없는 컬럼 `client_id`
  추측. 성공 시 `EXTRACT(YEAR FROM registered_at)` 정답 SQL).
  `seed=0`·`temperature=0`에서도 생성이 흔들린다 — model.json의 "seed로 1/5 고정"
  메모보다 실제 변동이 크다.
- 둘 다 어느 채점 축도 움직이지 않는다 — 순수하게 유저가 받는 결과의 문제다.
- **수정은 이 티켓에서 하지 않는다.** 동기가 회귀 관측이면 D7 동선이고, 프롬프트
  변경은 nl2sql의 ok/error를 바꿔 병렬 승격(`HAS_CONTENT`)을 타고 라우팅 축을 움직일
  수 있다 — "24/30 내려가지 않는다" 제약의 재측정 비용이 따라온다. 고치려면 별도
  티켓에서 구조·엣지 논거로 출발한다.
