# 결정 문서 — 라우터 배치: 게이트웨이형 vs 조언자형

> **상태: 공통부 구현 후 재평가 (2026-08-12).** [design.md](./design.md) D1의 미확정 부분. **에이전트 구조만 여기에 종속되고**, 도구 3종 핸들러·규칙 판별 함수·부분 응답 스키마는 두 안에서 동일하다.
>
> **쟁점 한 줄**: 규칙 라우터가 판별한 뒤 **도구를 직접 실행하는가(실행자)**, **어느 도구를 쓸지만 알려주는가(조언자)**.
>
> 확정되어 흔들리지 않는 전제: 라우터는 에이전트 밖 **MCP 도구**이고, 도구 선택은 **규칙**이 하며(LLM 아님), 등록 도구는 **4개**다. 두 안 모두 이를 만족한다.

---

## 1. 표준 용어에서의 위치

이 논쟁은 우리가 처음 만난 문제가 아니다. 여러 표준·관행에 대응물이 있고, 그 이름을 빌리면 논의가 정확해진다.

### 1.1 네트워크 — 가장 정확한 대응

| | A안 | B안 |
|---|---|---|
| **DNS 해석 방식** (RFC 1034) | **재귀적 질의(recursive)** — 리졸버가 대신 끝까지 물어보고 최종 답만 돌려준다 | **반복적 질의(iterative)** — 리졸버가 "저 네임서버에 물어봐"라는 **referral**만 준다. 클라이언트가 다시 질의 |
| **HTTP** | **리버스 프록시** — 클라이언트는 한 번 요청, 프록시가 뒤에서 대신 처리해 결과를 돌려줌 | **302 리다이렉트** — "저 주소로 다시 요청하라"는 응답. 클라이언트가 재요청 |

DNS 비유가 특히 정확하다. 재귀 리졸버는 클라이언트를 단순하게 만들지만 중간 과정이 보이지 않고, 반복 질의는 클라이언트가 각 단계를 관측하고 제어할 수 있다. **우리 트레이드오프와 정확히 같은 구조다.**

### 1.2 소프트웨어 아키텍처 패턴

| 패턴 | 대응 | 설명 |
|---|---|---|
| **Facade** | A안 | 복잡한 하위 시스템을 단일 진입점 뒤로 감춘다. 호출자는 내부를 모른다 |
| **Orchestration** (중앙 조정) | A안 — 조정자가 서버 | 하나의 조정자가 흐름을 통제한다. 조정 로직이 한 곳에 모임 |
| **Mediator / Dispatcher** | B안 | 중재자가 "누가 처리할지"를 결정하고, 실행은 호출자나 처리자가 한다 |
| **Strategy 선택 분리** | B안 | 전략 *선택*과 전략 *실행*을 다른 컴포넌트로 나눈다 |
| **Service Discovery** | B안 | 레지스트리가 "이 서비스는 여기 있다"를 알려주고, 실제 호출은 클라이언트가 한다 |

B안은 **조정 주체가 에이전트로 옮겨간 orchestration**이지 choreography(각 참여자가 이벤트에 자율 반응)는 아니다. 두 안 다 중앙 조정이며, **조정자가 서버냐 에이전트냐**가 다를 뿐이다.

### 1.3 MCP 스펙에서의 용어

스펙([정리본](./references/mcp-spec.md))이 정의하는 구성요소는 셋이다.

- **Host**: 연결을 시작하는 LLM 애플리케이션 → 우리 **AI 에이전트**
- **Client**: Host 안의 커넥터
- **Server**: 컨텍스트·기능을 제공하는 서비스 → 우리 **MCP 서버**

**스펙에 "라우터"라는 개념은 없다.** 라우터는 우리 도메인 용어이며, MCP 관점에서는 어느 안이든 그냥 **Tool 하나**다.

주의할 문구가 하나 있다. 스펙은 Tools를 이렇게 규정한다.

> Tools in MCP are designed to be **model-controlled**, meaning that the language model can discover and invoke tools automatically... However, implementations are free to expose tools through any interface pattern that suits their needs — **the protocol itself does not mandate any specific user interaction model.**

즉 MCP의 기본 상정은 "모델이 도구를 고른다"인데, 과제는 "규칙 기반 라우터"를 요구한다. **두 안 모두 이 기본 상정에서 벗어나며, 뒷문장 덕분에 두 안 모두 스펙 위반은 아니다.** 이 점에서 A와 B는 동률이다 — 어느 쪽도 "더 MCP답다"고 주장할 수 없다.

다만 결이 다르다. A안은 도구를 하나만 쓰게 해서 선택 자체를 없앤다. B안은 도구 선택 결과를 데이터로 만들어 모델 대신 코드가 집행한다.

## 2. 동작 방식

### 2.1 A안 — 게이트웨이형

```
사용자 질문
   ↓
AI 에이전트
   ↓  ① ask(question)                      ← MCP 왕복 1회
MCP 서버
   └ ask 핸들러
       ├ 규칙 판별 → "nl2sql"
       ├ nl2sql 내부 함수 호출 → LLM SQL 생성 → PostgreSQL 실행
       └ 결과 + 라우팅 메타데이터 반환
   ↓
에이전트 LLM이 컨텍스트로 최종 답변 생성
```

주고받는 내용:

```jsonc
// → tools/call
{ "name": "ask", "arguments": { "question": "서울 지역 매출 상위 5개 고객사를 알려줘" } }

// ← 결과
{
  "content": [{ "type": "text", "text": "..." }],
  "structuredContent": {
    "routed_to": "nl2sql",              // 라우팅 결과는 메타데이터로 실어 보내야 보인다
    "rows": [ { "name": "Client-A", "total": 128000000 }, ... ],
    "sql": "SELECT ...",
    "sources": ["contracts", "clients"]
  }
}
```

### 2.2 B안 — 조언자형

```
사용자 질문
   ↓
AI 에이전트
   ↓  ① route(question)                    ← MCP 왕복 1
MCP 서버 — route 핸들러: 규칙 판별만
   ↓  { tool: "nl2sql", arguments: {...}, confidence: 0.9 }
에이전트 — 지시대로 호출 (실행 주체는 아래 B1/B2)
   ↓  ② nl2sql(arguments)                  ← MCP 왕복 2
MCP 서버 — nl2sql 핸들러 → LLM SQL 생성 → PostgreSQL
   ↓  결과
에이전트 LLM이 결과로 최종 답변 생성
```

주고받는 내용:

```jsonc
// → tools/call
{ "name": "route", "arguments": { "question": "서울 지역 매출 상위 5개 고객사를 알려줘" } }

// ← 결과 (실행 없이 지시만)
{
  "content": [{ "type": "text", "text": "nl2sql" }],
  "structuredContent": {
    "decision": "single",                 // single | parallel | out_of_scope
    "tools": [{ "name": "nl2sql", "arguments": { "question": "..." } }],
    "confidence": 0.9,
    "matched_rule": "aggregation+region"
  }
}

// → tools/call (에이전트가 지시대로)
{ "name": "nl2sql", "arguments": { "question": "서울 지역 매출 상위 5개 고객사를 알려줘" } }
```

### 2.3 B안의 하위 갈래 — 지시를 누가 집행하나

| 갈래 | 집행 주체 | 평가 |
|---|---|---|
| **B1** | 에이전트 **LLM**이 `route` 응답을 읽고 스스로 다음 도구를 호출 | **비권장.** 라우터를 두고도 소형 LLM에게 최종 선택을 맡기는 형태다. 라우터가 정답을 줘도 LLM이 다르게 부를 수 있어, 규칙 기반 라우팅의 이점을 스스로 깎는다 |
| **B2** | 에이전트 **코드**가 `route` 응답의 `tools[]`를 그대로 호출 | **권장.** LLM은 최종 답변 생성에만 관여한다. A안과 동일한 안전성을 가지면서 라우팅 결과가 관측된다 |

이하 "B안"은 B2를 가리킨다.

## 3. 비교

### 3.1 구조·동작

| 축 | A안 (게이트웨이) | B안 (조언자) |
|---|---|---|
| MCP 왕복 | 1회 | 2회 |
| 조정 로직 위치 | MCP 서버 | 에이전트 |
| 소형 LLM이 도구를 고르는가 | 아니오 (선택지가 `ask` 하나) | 아니오 (코드가 집행) |
| 라우팅 결과 가시성 | **낮음** — 메타데이터로 실어야 보임 | **높음** — 독립된 MCP 응답 |
| 에이전트 복잡도 | 최소 | 2단계 오케스트레이션 코드 필요 |
| 실패 지점 | 1곳 | 2곳 |
| 병렬 호출(D3) 수행 위치 | 서버 내부 — 자연스러움 | 에이전트가 `tools[]`를 병렬 호출 |
| 도구 3종의 성격 | 검증·시연용 창구 (평소 미사용) | **실사용 경로** |
| 레이턴시 | 왕복 1 | 왕복 2 (stdio 로컬이라 실질 차이 미미) |
| 에이전트 LLM 호출 수 | 1회 (최종 답변) | 1회 (동일 — B2는 코드가 집행하므로) |

### 3.2 숨은 비용 — 중간 산출물 재계산

B안에서 `route`가 판별을 위해 중간 산출물(예: 질문 임베딩)을 만든다면, 이어지는 두 번째 호출이 같은 것을 다시 계산해야 한다. MCP는 프로토콜 수준 세션이 없으므로([mcp-spec.md](./references/mcp-spec.md)의 상태 관리 절) 이를 넘기려면 핸들 패턴(첫 호출이 핸들 반환 → 다음 호출 인자로 전달)이 필요해지고, 그러면 B안의 단순함이 사라진다.

**우리 라우터에는 이 비용이 없다.** 판별 규칙이 **요구 출력 형태** 기반 키워드·패턴 매칭으로 확정되어(D9) 중간 산출물이 생기지 않는다. 순수 규칙 라우터를 유지하는 한 B안의 실질 추가 비용은 왕복 1회뿐이다. A안은 같은 프로세스 안에서 이어지므로 이 문제가 원천적으로 없다.

### 3.3 엣지케이스 대응 ([edge-cases.md](./edge-cases.md) 17건 대조)

| 케이스 | A안 | B안 |
|---|---|---|
| **X1 관계 카운트 / X2 관계 조회** (동일 중복) | 규칙이 단일 선택 — 병렬 없음 | 동일 |
| **X3 사건 조회 / X4 개체 지목 서술** (상보 중복) | `ask` 내부에서 병렬 호출·병합 | `route`가 `tools: [2개]` 반환 → 에이전트가 병렬 호출·병합. **병합 로직이 에이전트로 감** |
| **X5 부분 응답** (요구 형태 미충족) | `ask`가 도구 결과를 보고 조립 — **적용 지점 하나** | 에이전트가 조립. `route` 응답에 `expected_form`을 실으면 자산 의미 없이 기계적 판정은 가능하지만, **조립 코드가 에이전트에 생긴다** |
| **R1 무매칭** (후보 도구 없음) | `ask`가 `out_of_scope` 응답 반환 | `route`가 `decision: "out_of_scope"`, `tools: []` 반환 → 에이전트가 두 번째 호출을 하지 않음. **거절이 더 명시적으로 드러남** |
| **R2 애매** (X3·X4 해당 시 병렬) | X3·X4와 동일 | X3·X4와 동일 |
| **R3 복수 도구 질문** | R2와 동일 | R2와 동일 |
| **T1 SQL 생성 실패** | `ask` 안에서 nl2sql 재시도 처리 | `nl2sql` 도구 안에서 처리 — 두 안 동일 |
| **T2 SELECT 외 차단** | 도구 내부 — 동일 | 동일 |
| **T3 결과 0행** | `ask`가 "0건" 정상 응답으로 감쌈 | `nl2sql`이 직접 반환 — **응답 형태가 도구별로 노출되므로 스키마를 각각 정의해야 함** |
| **T4 유사도 미달** | 동일 | 동일 |
| **T5 그래프 개체 부재** | 동일 | 동일 |
| **T7 그래프 관계 부재** (개체는 있음) | `ask`가 인접 관계를 보고 X5로 승격 — **판정이 한 곳** | `knowledge_graph`가 "관계 없음"을 반환하고 **에이전트가 인접 사실을 다시 조회해 승격 판정** — 승격 로직이 에이전트로 감 |
| **T6 인프라 오류** | `ask` 한 곳에서 에러 타입 통일 | **두 호출 각각에서 발생 가능** — 에러 처리 코드가 두 곳 |
| **Q1 환각 방지 (출처 메타데이터)** | `ask` 응답에 일괄 부착 | 도구별 응답에 각각 부착 + 라우팅 정보는 `route` 응답에 |
| **Q2 컨텍스트 초과 (TACC 절사)** | **`ask`가 최종 반환 직전 일괄 절사 — 적용 지점이 하나** | 도구별 절사 + 에이전트 병합 시 절사 — **적용 지점이 분산** |
| **Q3 거절 수신 시 모름 답변** | 동일 | 동일 |

**요약**: R1(거절)은 B안이 더 명확하고, **Q2(TACC 절사)·T6(에러 통일)·X5(부분 응답 조립)·T7(승격 판정)은 A안이 유리하다.** 조립·병합 지점이 A안은 한 곳, B안은 셋(병렬 병합·부분 응답·절사)으로 갈리며, 4.5·4.6절의 저울이 여기서 나온다. TACC가 과제 요구사항이라는 점에서 Q2는 가볍지 않다.

### 3.4 검증·시연

| 항목 | A안 | B안 |
|---|---|---|
| **라우터 정확도 측정** (questions.json 30개, D7 회귀 세트) | `ask` 내부 판단을 응답 메타데이터로 꺼내야 측정 가능 | **`route`만 30번 호출해 `tools[0].name`을 기대값과 비교하면 끝. DB·LLM 없이도 라우터 단위 테스트가 된다** |
| 도구 3종 단위 테스트 | 개별 도구 직접 호출 (D2로 등록되어 있어 가능) | 동일 |
| 시연 가시성 | 라우팅 판단을 로그·메타데이터로 따로 보여줘야 함 | **MCP 통신 로그에 라우팅 결정이 그대로 찍힘** |
| 통합 테스트 | 한 번 호출로 끝 — 단순 | 2단계 시나리오 필요 |

B안의 가장 큰 실질 이점이 여기다. **라우터를 독립적으로, 값싸게 테스트할 수 있다.** A안에서도 라우터 판별 함수를 직접 단위 테스트할 수는 있지만, 그건 MCP를 거치지 않은 내부 함수 테스트다.

### 3.5 과제 문면 대조

블로그 흐름도:

```
사용자 질문 → AI 에이전트 → 라우터 → MCP 서버 → PostgreSQL → 답변 반환
```

라우터가 에이전트와 MCP 서버 **사이의 독립 단계**로 그려져 있다. 문자 그대로는 **B안이 더 가깝다.** A안은 라우터가 서버 *안*에 있어 그림과 층위가 어긋나며, 심사에서 설명이 필요하다.

| 문면 | A안 | B안 |
|---|---|---|
| 흐름도 (라우터가 독립 단계) | 층위 불일치 — 설명 필요 | **1:1 대응** |
| KOSSA 구현 목표 — 산출물 넷(벡터·NL2SQL·KG·에이전트)에 **라우터가 없다.** 라우터는 넷을 잇는 배선으로 예시에만 등장 | 배선이 서버 내부 사건이 됨 — 설명 필요 | **배선이 독립 단계로 드러남** |
| README 표 (라우터를 "MCP 도구"로 표기) | 충족 | 충족 |
| 블로그 "3개의 MCP 도구를 구현합니다" | 충족 (등록됨) | 충족 + **실제로 쓰임** |
| KOSSA "규칙 기반 라우터로 도구 자동 선택" | 충족 | 충족 |
| "선택적 컨텍스트 큐레이션(TACC)" | **적용 지점 하나 (`ask` 반환 직전)** | 적용 지점 분산 |

**KOSSA 목표 행은 약한 신호로만 쓴다.** 요강 "개발과제 예시" 5개는 층위가 고르지 않다 — 1번은 인프라, 4번은 연동, 5번은 최적화 기법이다. **항목이 분리됐다는 것이 곧 아키텍처 층위 분리는 아니다.** 반대편에는 라우터를 "MCP 도구"로 직접 표기한 README 표가 있고, D1은 그쪽을 근거로 확정했다. 이 행이 뒤집는 것은 없고, 재평가 시 B안 쪽에 얹히는 재료 하나다.

### 3.6 문헌 근거

| 근거 | A안 | B안 |
|---|---|---|
| Shen et al., Small LLMs Are Weak Tool Learners (EMNLP 2024) — 소형 LLM은 단일 에이전트로 계획·호출·요약을 못하므로 **역할 분해** 필요 | 충족 (LLM은 답변 생성만) | 충족. **"역할 분해"라는 표현 자체는 B안에 더 가깝게 읽힘** |
| Mem2ActBench (arXiv:2601.19935) — 후보 도구 1→5개일 때 hard negative 조건 94.50%→69.75% | LLM 선택지 1개 | LLM 선택 없음 (B2). **B1이면 해당됨 → B1 비권장 근거** |
| Pylon-7 (필수 참조 [2]) — MCP는 계층 간 전이를 표준화하는 **게이트웨이** | 이름 그대로 대응 | 게이트웨이 개념과는 덜 맞음 |
| Pylon-7 — Stage A(결정적 규칙) → Stage B(AI 판단) 파이프라인 | 한 호출 안에서 A→B | **단계가 관측 가능하게 분리 — Stage 구분이 실물로 드러남** |
| Toolken+ REJECT (Findings of EMNLP 2024), BFCL irrelevance (ICML 2025) | `ask` 응답에 거절 타입 | `route` 응답에 거절 타입 — **거절이 실행 전에 일어남이 명시적** |

**문헌만으로는 결론이 나지 않는다.** 핵심 요건("소형 LLM에게 도구 선택을 맡기지 않는다")을 A와 B2가 똑같이 만족하기 때문이다. Pylon-7의 "게이트웨이" 명명은 A안에, "Stage 분리"는 B안에 각각 유리하게 읽힌다.

## 4. 결정 재료

### 4.1 각 안이 사는 것과 파는 것

**A안은 단순함을 산다.** 에이전트가 얇아지고, TACC 절사와 에러 처리가 한 곳에 모이고, 실패 지점이 하나이며, 병렬 병합이 서버 안에서 끝난다. **파는 것은 관측성이다** — 라우팅 판단이 서버 내부 사건이 되어, 보여주려면 따로 실어 내보내야 한다.

**B안은 관측성을 산다.** 라우팅 결정이 독립된 MCP 응답이 되어 시연에 그대로 드러나고, 라우터를 DB·LLM 없이 단위 테스트할 수 있고, 도구 3종이 실사용 경로가 되며, 과제 흐름도와 층위가 일치한다. **파는 것은 단순함이다** — 에이전트에 오케스트레이션 코드가 생기고, TACC 절사와 에러 처리 지점이 분산되며, 실패 지점이 둘로 늘어난다.

### 4.2 선택 기준

| 이렇게 판단한다면 | 선택 |
|---|---|
| 구현 리스크를 최소화하고 에이전트를 얇게 유지하고 싶다 | **A안** |
| TACC 적용과 에러 처리를 한 곳에서 통제하는 것이 중요하다 | **A안** |
| 심사에서 "라우터가 이렇게 판단했다"를 눈에 보이게 시연하고 싶다 | **B안** |
| questions.json 30개로 라우터 정확도를 값싸고 반복 가능하게 재고 싶다 | **B안** |
| 과제 흐름도와 구조가 1:1로 대응하는 편이 설명하기 쉽다 | **B안** |
| 도구 3종이 "등록만 되고 안 쓰이는" 상태가 마음에 걸린다 | **B안** |

### 4.3 되돌릴 수 있는가

**부분적으로 그렇다.** 도구 3종의 핸들러 로직(`vector_search`·`nl2sql`·`knowledge_graph`)은 두 안에서 완전히 동일하다. 규칙 판별 함수도 동일하다. 달라지는 것은 **그 둘을 어떻게 잇느냐**뿐이다.

- A → B 전환: `ask` 핸들러에서 실행부를 떼어내고 판별 결과를 반환하도록 바꾼 뒤, 에이전트에 집행 코드를 추가한다.
- B → A 전환: `route` 핸들러 안에서 판별 후 도구 함수를 직접 부르도록 잇는다.

**따라서 이 결정의 비가역성은 낮다.** 다만 에이전트 코드 구조와 테스트 코드가 함께 바뀌므로, 구현이 진행된 뒤 뒤집으면 그만큼 손실이 난다 — 그래서 구현 착수 전에 정한다.

### 4.4 하이브리드는?

`ask`와 `route`를 **둘 다** 등록하는 방안이 이론상 가능하다(도구 5개). `route`로 라우팅만 테스트하고, 실사용은 `ask`로 하는 식이다.

**권하지 않는다.** 판별 로직은 공유하더라도 실행 경로가 둘이 되어 테스트 대상이 늘고, "어느 것이 진짜 경로인가"라는 질문을 심사에서 받는다. D2가 도구 4개로 정리된 명분(과제 문면 충족)도 흐려진다. 다만 **A안을 택하더라도 `ask` 응답의 `structuredContent`에 `routed_to`·`matched_rule`을 반드시 실어** 라우팅 판단을 관측 가능하게 만들면, B안 이점의 상당 부분을 값싸게 회수할 수 있다.

### 4.5 데이터 특성이 미는 방향

| 재료 | 어느 쪽에 유리한가 |
|---|---|
| **부분 응답**(D10)으로 병합 지점이 셋이다 — 병렬 병합(X3·X4) + 부분 응답 조립 + TACC 절사 | **A안.** B안이면 셋 다 에이전트로 간다. 다만 `route` 응답에 `expected_form`을 실어 보내면 에이전트는 자산 의미를 몰라도 기계적으로 조립할 수 있으므로, **"에이전트가 두꺼워진다"까지가 정확한 서술이고 "자산 의미를 알아야 한다"는 과장이다** |
| **회귀 2축 분리**(D7) — 라우팅 축의 독립 측정이 필요하다 | **B안.** `route`만 30번 호출하면 끝. 단 A안도 판별을 순수 함수로 분리하면 같은 비용이므로 **동률에 가깝다** |
| **부분 응답은 관측성이 중요한 상태**다 — "왜 이 답이 부분인가"를 설명해야 한다 | **B안.** `route` 응답에 기대 형태가, 도구 응답에 부재가 각각 찍힌다 |
| **병렬(X3·X4)이 눈에 보인다** | **B안.** MCP 로그에 병렬 호출이 그대로 찍힌다. 원문이 병렬을 정의하지 않은 건 사실이지만 **심사위원은 요강에서 그 단어를 봤다** — 눈에 보이는 것 자체가 방어 자산이다 |
| **격자 실측이 X4보다 X5를 밀어준다** | **A안.** X4(개체 지목 서술)가 발동하려면 문서에 그 개체 **와** 그 형태가 둘 다 있어야 하는데, 격자는 10/60·30/90이다 ([dataset-analysis.md](./dataset-analysis.md) 3장). **X4는 예상보다 덜 발동하고 X5(부분 응답)가 더 자주 발생한다** — 그리고 3.3절 요약대로 X5 조립은 A안이 유리하다. 위 "부분 응답 병합 지점이 셋" 행과 같은 방향이다 |

### 4.6 저울의 비대칭

**A안: 복잡도가 한 곳에 모인다 / B안: 판단 과정이 보인다.**

비대칭이 하나 있다 — B안의 가시성은 A안에서 `structuredContent` + 로깅으로 상당 부분 회수되지만, **A안의 복잡도 집중은 B안에서 회수할 방법이 없다**(에이전트가 병합을 하는 것은 구조적이다). 이 비대칭 때문에 A안이 근소하게 앞선다고 본다.

다만 **"명확하다"고 말할 수는 없다.**

### 4.7 확장 가능성 — 재평가에서 추가된 축 (2026-08-21)

문서를 처음 쓸 때 없던 기준이다. **새 요구가 들어올 때 무엇이 얼마나 바뀌는가.**

공통부가 만들어진 뒤라 이것은 잴 수 있다 — 두 안을 다 만들고 **같은 확장을
양쪽에 넣어** 변경 파급을 세면 된다. 확장 시나리오는 지어내지 않고 이 프로젝트가
**실제로 겪은 것**을 썼다: `ambiguous_entity` — `박성민` 이 동명이인 2명이고
한쪽만 `LEADS` 를 갖는다. 하나를 골라 답하면 조용히 틀린다.

| 확장 | 공통 비용 | A안 추가 | B안 추가 |
|---|---|---:|---:|
| **응답 상태 추가** (`ambiguous_entity`) | 2파일 27줄 | **1파일 1줄** | **2파일 10줄** |
| 도구 추가 (4번째 데이터 자산) | 4곳 | 0 | 0 |
| 병합 정책 변경 (병렬 2 → 3) | 1곳 | 0 | 0 |

**갈리는 축은 응답 상태 하나뿐이다.** 도구 추가와 병합 정책은 두 안 모두
`composition.runTool` 과 `MAX_PARALLEL` 을 지나가므로 파급이 같다 — 실측했다.

**차이의 이유가 구조적이다.** `route` 는 도구를 실행하지 않으므로 **상태를 미리 알 수
없다.** 그래서 B안에서는 새 상태가 생길 때마다 ① `route` 응답의 `possible_states` 에
예고하고 ② 에이전트가 그것을 처리해야 한다. A안은 서버가 알고 에이전트는 `status` 를
읽기만 한다.

**그리고 이 프로젝트는 응답 상태가 계속 늘어난다.** `X5`(부분 응답) · `T7`(관계 부재) ·
`R1`(거절) · `T5`(개체 부재)에 이어, 도구를 실제로 돌리다 `ambiguous_entity` 를 찾았다.
확장의 실제 형태가 그쪽이고, 그 축에서 A안이 앞선다.

## 5. 결정 기록

- **결정**: **A안 — 게이트웨이형.** 라우터 도구 이름은 `ask`.
- **결정일**: 2026-08-21 (보류 2026-08-12 → 재평가)
- **재평가가 확인한 것** — 2026-08-12 이 "만들어 봐야 안다"고 한 입력 둘:
  1. **병렬 발동률은 낮다.** 회귀 30문항(현실 분포)에서 **2건(6.7%)**, 엣지 29문항
     (병렬을 일부러 넣은 세트)에서 6건. *"드물면 A안"* 쪽이다.
  2. **부분 응답 조립은 지저분하지 않다 — 도구 안에서 끝난다.** `vector_search` 가
     빈손일 때 `knowledge_graph` 를 내부에서 불러 `adjacent_facts` 를 채우고 완성된
     `PartialResult` 를 반환한다. **4.5 의 "병합 지점이 셋" 전제 중 하나가 무너졌다** —
     부분 응답 조립은 A/B 어느 쪽에서도 에이전트로 가지 않는다.
- **저울이 바뀐 것** — 양쪽이 이점을 하나씩 잃었다:
  - **A안**: "에이전트가 얇아진다"가 **약해졌다** (병렬 6.7% · 부분 응답은 도구가 조립).
  - **B안**: "라우터를 DB·LLM 없이 단위 테스트할 수 있다"가 **무효가 됐다** — D12 라우터는
    임베딩(Ollama)과 문서 벡터 조회(DB)를 둘 다 요구한다.
  - **동률 확인**: 4.5 가 단서를 단 *"A안도 판별을 순수 함수로 분리하면 같은 비용"* 은
    실증됐다. `src/router.ts` 를 모듈로 분리하니 `run_router.py` 가 라우팅 축만 독립 측정한다.
  - **정정**: 재평가 초기에 *"병렬 확정이 실행에 종속되므로 B안이 불리하다"* 고 보았으나
    **틀렸다.** 접속 탐지만으로도 도구 짝이 맞는다(엣지 라우팅 25/29 — 실행 확인과 동률).
    실행 확인이 바꾸는 것은 **상태 라벨**(실행 축 22 → 27)이지 도구 선택이 아니다.
- **결정 근거**: 위 둘로는 갈리지 않았다. **가른 것은 4.7 의 확장 가능성이다** —
  새 응답 상태 하나를 넣는 데 A안 1줄, B안 10줄이고, 그 차이가 구조적이며,
  이 프로젝트는 응답 상태가 계속 늘어난다.
- **의무 조항**: A안이 파는 것은 관측성이므로 **회수책을 필수로 단다** (4.4).
  `ask` 응답의 `structuredContent` 에 `routed_to` · `matched_rule` · `why` 를 반드시 싣는다.
  `src/gateway.ts` 가 이를 구현한다.
- **하이브리드는 채택하지 않는다** (4.4). `route` 와 에이전트 집행부는 재평가 측정을 위해
  만들었다가 **삭제했다.** 실행 경로가 둘이면 "어느 것이 진짜인가"를 심사에서 받는다.
- **"명확하다"고 말하지 않는다.** 4.6 의 그 단서는 지금도 맞다. 다만 미룰 이유는 사라졌다.

결정 후 이 절을 채우고, [design.md](./design.md) D1을 확정 상태로 바꾸며, D3의 조건부 표기(병렬 수행 위치)를 확정 문구로 바꾼다. `CONTEXT.md`의 라우터 정의도 선택된 한 형태로 정리한다.
