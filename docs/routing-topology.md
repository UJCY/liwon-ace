# 라우터 배치 방식 비교 — 게이트웨이형 vs 조언자형

> 열린 항목 **라우터 배치**([design.md](./design.md) D1) 결정용 비교 문서. 이전에 게이트웨이형으로 확정했던 것을 재개방했다.
>
> 쟁점 한 줄: **라우터가 도구를 직접 실행하고 결과까지 돌려주는가(실행자), 아니면 어느 도구를 쓸지만 알려주는가(조언자).**

## 두 안

### A안 — 게이트웨이형 (라우터가 실행자)

`ask(question)` 하나가 라우팅·도구 실행·결과 반환을 한 번에 끝낸다. 에이전트의 MCP 왕복은 1회다.

```
에이전트 ──ask(question)──▶ MCP 서버
                              └ ask 내부: 규칙 판별 → 도구 호출 → PostgreSQL → 결과
에이전트 ◀──── 컨텍스트 ────┘
에이전트 LLM이 컨텍스트로 최종 답변 생성
```

### B안 — 조언자형 (라우터가 조언자)

`route(question)`은 **어느 도구를 어떤 인자로 부를지만** 알려준다. 에이전트가 그 지시대로 도구를 호출한다. MCP 왕복은 2회다.

```
에이전트 ──route(question)──▶ MCP 서버 (규칙 판별만)
에이전트 ◀── {tool:"nl2sql", args:{...}, confidence:0.9} ──┘
에이전트 ──nl2sql(args)──▶ MCP 서버 → PostgreSQL
에이전트 ◀──── 결과 ────┘
에이전트 LLM이 결과로 최종 답변 생성
```

**B안에는 갈래가 하나 더 있다** — 라우터 지시를 누가 실행하느냐다. 이 선택이 B안의 성격을 크게 바꾼다.

- **B1 (LLM이 실행)**: 에이전트 LLM이 `route` 응답을 읽고 스스로 다음 도구를 호출한다. 표준 MCP 방식이지만 **소형 LLM에게 도구 선택을 다시 맡기는 셈**이 된다 — 라우터가 정답을 알려줘도 LLM이 다르게 부를 수 있다.
- **B2 (코드가 실행)**: 에이전트 쪽 코드가 `route` 응답의 `tool` 이름을 그대로 호출한다. LLM은 선택에 관여하지 않고 최종 답변 생성에만 쓰인다.

## 비교

| 축 | A안 (게이트웨이) | B안 (조언자) |
|---|---|---|
| **MCP 왕복** | 1회 | 2회 |
| **소형 LLM이 도구를 고르는가** | 아니오 — 선택지가 `ask` 하나뿐 | **B1: 예** (라우터 조언을 받지만 최종 호출은 LLM) / **B2: 아니오** |
| **라우팅 결과의 가시성** | 낮음 — 서버 내부에서 일어나고, 응답 메타데이터로 내보내야 보인다 | **높음 — 라우팅 결과가 독립된 MCP 응답으로 관측된다** |
| **에이전트 복잡도** | 최소. `ask` 부르고 답 생성 | 2단계 오케스트레이션 필요 (B2는 실행 코드까지) |
| **병렬 호출(D3) 구현 위치** | 서버 내부. 자연스러움 | 에이전트가 여러 도구를 호출해야 함 — 오케스트레이션이 에이전트로 넘어감 |
| **도구 3종 등록 명분** | 검증·시연용 창구 (평소 미사용) | **실사용 경로** — 등록 이유가 더 분명해짐 |
| **에이전트가 라우팅을 무시·재정의** | 불가 | 가능 — 장점이자 위험 |
| **실패 지점** | 1곳 (`ask`) | 2곳 (route, 도구 호출) |
| **레이턴시** | 왕복 1회 | 왕복 2회 (stdio 로컬이면 차이 미미) |
| **토큰 비용** | 에이전트 LLM 호출 1회 | B1은 LLM 호출 2회 이상 / B2는 1회 |

## 과제 문면 대조

블로그 흐름도는 이렇다.

```
사용자 질문 → AI 에이전트 → 라우터 → MCP 서버 → PostgreSQL → 답변 반환
```

**라우터가 에이전트와 MCP 서버 사이의 독립 단계로 그려져 있다.** 문자 그대로 읽으면 A안(라우터가 서버 *안*)보다 B안이 흐름도에 가깝다. 다만 데이터셋 README는 라우터를 "MCP 도구"로 표기하므로, 라우터가 MCP 밖 별도 모듈은 아니다 — 두 안 모두 라우터를 MCP 도구로 두는 점은 같다.

KOSSA 요강의 "MCP Parallel 패턴"은 A안이 자연스럽다. B안에서 병렬 호출을 하려면 에이전트가 여러 도구를 동시에 부르는 오케스트레이션을 해야 한다.

## 문헌 근거

| 근거 | 함의 |
|---|---|
| Shen et al., Small LLMs Are Weak Tool Learners (EMNLP 2024) — 소형 LLM은 계획·호출·요약을 단일 에이전트로 감당하지 못하므로 **역할을 분해**해야 한다 | **B1에 불리.** 다만 논문이 말하는 역할 분해는 "여러 전문 모듈로 나눠라"이므로, route와 실행을 분리한 **B2는 오히려 이 논지에 부합**한다고도 읽힌다 |
| Mem2ActBench (arXiv:2601.19935) Table 5 — 후보 도구 1→5개일 때 hard negative 조건에서 94.50%→69.75%, random negative는 무변화 | A안·B2는 LLM에게 선택을 안 시키므로 해당 없음. **B1은 LLM이 3종 중 고르는 상황이 생긴다** — 단, 라우터가 이미 정답을 제시한 상태라 순수 선택 문제보다는 쉬움 |
| Pylon-7 (필수 참조 [2]) — MCP는 계층 간 전이를 표준화하는 **게이트웨이** | A안의 이름 그대로. 다만 Pylon-7의 Stage A(결정적 규칙) → Stage B(AI 판단) 파이프라인은 **단계가 관측 가능하게 분리된 형태**여서 B안과도 맞는다 |
| Toolken+ REJECT (Findings of EMNLP 2024), BFCL irrelevance (ICML 2025) | 무매칭 거절(D6)은 두 안 모두 구현 가능. A안은 `ask` 응답에, B안은 `route` 응답에 거절 타입을 담는다 |

**문헌만으로는 A와 B2 사이에 결정적 우열이 없다.** 둘 다 "소형 LLM에게 도구 선택을 맡기지 않는다"는 핵심 요건을 만족한다. B1만 명확히 불리하다.

## 심사 관점

| 관점 | A안 | B안 |
|---|---|---|
| 흐름도 일치 | 라우터가 서버 안이라 그림과 층위가 다름 — 설명 필요 | 그림과 단계가 1:1 대응 |
| "도구 3종 구현" 요구 | 3종이 평소 안 쓰이는 창구라 "왜 등록했나" 질문 여지 | 3종이 실제 호출 경로 — 명분이 분명 |
| 시연 가시성 | 라우팅 판단을 보여주려면 로그·메타데이터를 따로 노출해야 함 | **라우팅 결과가 MCP 응답으로 그대로 보임 — 시연에 유리** |
| 라우터 정확도 측정 (questions.json 30개) | `ask` 내부 판단을 꺼내야 측정 가능 | `route` 응답만 보면 바로 측정 — **D7 회귀 검증이 단순해짐** |

## 판단 재료 정리

**A안이 유리한 지점**: 에이전트가 단순하다. 병렬 호출(D3)이 서버 안에서 끝난다. 실패 지점이 하나다. 왕복이 적다.

**B안(B2)이 유리한 지점**: 라우팅 결과가 관측 가능해서 **시연과 검증이 쉽다**. 도구 3종 등록 명분이 분명하다. 과제 흐름도와 층위가 일치한다. 라우터 정확도를 questions.json으로 재는 일이 `route` 응답만 보면 끝난다.

**결정적 트레이드오프**: A안은 **단순함과 병렬 처리**를 얻고 관측성을 잃는다. B2안은 **관측성과 심사 설명력**을 얻고 에이전트에 오케스트레이션 코드를 추가한다. 왕복 비용은 stdio 로컬 실행이라 실질적 차이가 아니다.

**B1은 권하지 않는다** — 라우터를 두고도 소형 LLM에게 최종 선택을 맡기는 형태라, 규칙 기반 라우팅의 이점을 스스로 깎는다.

> 참고: 세 번째 안이었던 "라우터를 MCP 밖 에이전트 측 모듈로 두기"는 이전 세션에서 기각했다. README가 라우터를 MCP 도구로 표기하기 때문이다. 위 두 안은 모두 라우터를 MCP 도구로 유지한다.
